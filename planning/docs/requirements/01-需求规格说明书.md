## 1. 项目背景与目标

### 1.1 现状（从交付物反推的真实痛点）

用户当前用 Excel 完成 IDC 机房上架规划的全流程，V3→V13 共迭代 6 个大版本、跨 2026-06-04 至 2026-07-14 约 40 天。从版本演进可以清楚看到痛点累积的过程：

| 版本 | 文件名体现的能力演进 |
|---|---|
| V3 | 只有「设备数量清单」「机柜布局」「403设备上架图」——纯规划 |
| V8 | 文件名加入「上架点位图及连线表」——开始画 U 位图和连线 |
| V9 | 再加入「IP地址段规划」——开始做网络层规划 |
| V11 / V12 | 持续迭代修正 |
| V13（最新） | 8 个正式 sheet + 4 个「（旧）」备份 sheet，布线表 5127 行、连线表 5307 行 |

**关键观察：V13 里保留了 4 个「（旧）」sheet，说明用户在 Excel 里做版本管理已经很吃力。** 一个 sheet 复制成「xxx（旧）」就是他的人工 undo，这直接证明需要真正的版本/变更管理。

现存的具体痛点（每条都能在文件里找到证据）：

1. **数据严重冗余且不一致**
   - `布线表`（25 列，5127 行）与 `连线表(不含长度)`（13 列，5307 行）是**同一份连线数据的两份拷贝**。二者行数差 180 行，且 `连线表` 里有 5111 条是 `布线表` 里没有的（因为列组合不同导致去重失效）。同一根线在两个 sheet 里可能填了不同值。
   - 设备名称写法不统一：`带外交换机1`（608 行）vs `带外交换机 1`（76 行）vs `计算接入交换机(业务)-25` —— 中英文括号、有无空格混用。人工肉眼无法可靠去重。

2. **跨 sheet 靠人脑维持一致性**
   - `机房平面图` 定义了通道与机柜号的几何关系；`404房间1-3通道` 点位图逐 U 位画设备；`布线表` 里手填「本端通道/本端机柜/U位」。三者之间**没有任何公式引用**，全靠人填对。一旦机柜位置调整，要手工改三个 sheet。

3. **线长计算是半自动的，且最终值靠人工覆盖**
   - `布线表` 的 P/R/S/T 四列有活公式（详见 §3.3），但最终交付的「线缆长度」列 U 是**人工填的数**。实测：636 条跨机柜记录中，352 条 U 与公式值 T 相同，**289 条 U 被人为上调**（多为上调一档，如算出 20 实际要 25），另有少量下调。这些人工调整**没有任何记录**——谁改的、为什么改，全部丢失。

4. **耗材采购靠人工汇总**
   - `首期耗材需求清单` 是按「类型 × 长度」二维汇总的采购表，采购量 = 需求量 × 1.3 冗余，这个汇总关系是人工一条条数出来的。布线表一改，采购清单就得重数。

5. **多种连线表版式并存，无法复用**
   - 已发现 **5 种**互不兼容的连线表版式（详见 §3.5），分别是 V13 布线表、V13 连线表、政务外网 9 列式、11+12冷通道横向成对式、核心交换机标签式。每接一个新项目就要重新设计一遍表头。

6. **无法 3D/2D 直观查看**
   - 现有「机房平面图」是 Excel 单元格拼的 2D 示意图，能看出通道和柜号，但看不出机柜里的设备、看不出线缆走向。`404房间1-3通道` 是按 U 位逐行画的字符图，非常难读（305 行 × 84 列）。

### 1.2 产品目标

做一个**面向 IDC 实施交付场景**的规划与布线管理系统，核心价值主张是：

> **一份数据源 → 同时驱动 2D 图、3D 图、U 位图、布线表、耗材采购表，全部自动同步。**

具体目标（按用户原话拆解）：

| # | 用户原话 | 转化为需求目标 |
|---|---|---|
| G1 | "机房机柜与机器上架部署图示（能3D化、2D化展示）" | 同一份机柜/设备数据，同时渲染 2D 平面图 + 2D 机柜正视图(U位图) + 3D 机房全景 |
| G2 | "导出表格、导入表格" | 全量数据可导出 Excel（版式与现有交付物兼容），可反向导入并做差异分析 |
| G3 | "机器网卡端口、网络设备端口的统一管理" | 统一端口模型：服务器网卡端口 与 交换机端口 用同一套抽象，支持速率/介质/连接器/brokeout |
| G4 | "自动化完成布线表（机器和机器之间的连线表、能够导入和导出连线表）" | 从"连接意图"自动推导连线表，含线缆类型、长度、模块；支持导入现有连线表反向建模 |
| G5 | "这部分应该比较复杂" | 用户已识别到布线算法是难点，需要独立设计与充分验证 |
| G6 | "后期的管理维护，自动化巡检等等（现在不做）" | **明确排除在本期范围外**，但架构上要预留扩展点 |

## 2. 用户与使用场景

### 2.1 角色定义

| 角色 | 职责 | 关键诉求 |
|---|---|---|
| **IDC 规划工程师**（主用户） | 根据设备清单和机房条件，规划机柜分配、U 位摆放、网络拓扑与布线 | 快速试算布局、自动出布线表、改一处全联动 |
| **实施交付工程师**（次用户） | 按图施工，拉线、上架、贴标签 | 打印清晰的施工图、U 位图、带标签的连线表 |
| **采购/项目管理** | 按布线表汇总线缆与模块需求，下单 | 一键出耗材清单、支持 30% 冗余、能对比到货 |
| **运维工程师**（后期角色） | 接手后的日常维护、故障定位 | 端口占用查询、链路追踪（本期只做数据基础） |

### 2.2 核心使用场景（User Story）

**US-1 新建一个机房项目**
> 作为规划工程师，我要能从零建一个机房：定义房间 → 划通道 → 摆机柜 → 导入设备清单，然后系统自动给我一个空白的 U 位图。这样我不用再从 Excel 空白表格开始画格子。

验收：能建出与 `机房平面图` 等价的 403/404 双房间、14 条通道、每通道 25~27 个机柜的结构，含空调位、柱子位、走道。

**US-2 批量导入设备并自动上架**
> 作为规划工程师，我把设备清单（型号、数量、上联关系）导入后，希望系统按规则自动推荐每个设备放哪个机柜哪个 U 位，我确认或微调即可。

验收：导入 `首期设备清单` 的 22 类设备，系统给出上架建议；设备型号的 U 高（如 2U）能从型号库带出。

**US-3 定义连接意图并自动生成布线表**
> 作为规划工程师，我只需要声明"计算节点A的 25GE1 口接到业务接入交换机的某个口"，系统就自动算出：跨几个机柜、间隔几个机柜、机柜内用多长线、柜间用多长线、最终采购长度、两端各要什么光模块。

验收：对现有 5127 行布线表做**回归验证**——用系统重算，与人工值的一致率 ≥ 95%（跨机柜行的 O 列、P/R/S/T 列必须 100% 一致，U 列允许差异但需给出"人工上调"标记）。

**US-4 导入历史连线表反向建模**
> 作为工程师，接手一个已经在 Excel 里规划好的项目，我要能把现有的连线表导入系统，而不是重新录一遍。

验收：能导入 `政务外网区交换机连线表-0606.xlsx` 的 10 个 sheet（9 列版式）、`11+12冷通道（示例）.xlsx` 的连线表（横向成对版式）、以及 V13 布线表（25 列版式），导入后数据等价。

**US-5 改布局后自动重算**
> 作为规划工程师，我把某个机柜从通道1挪到通道3，希望所有相关连线的长度自动重算，并且告诉我哪些线变长了、需要重新采购。

验收：拖动一个机柜，系统列出受影响的所有连线（本端或对端在该柜），显示长度变化 diff，并更新耗材汇总。

**US-6 生成施工交付物**
> 作为实施工程师，我要打印：每个机柜的 U 位图（贴柜门用）、每个通道的连线表（按机柜分组）、线缆标签清单（按标签格式导出给标签打印机）。

验收：能导出可直接打印的 PDF/Excel，标签格式可配置（现有 3 种标签格式见 §3.5）。

**US-7 查看 3D 机房**
> 作为规划工程师/汇报对象，我要能旋转查看整个机房的 3D 效果，点一个机柜能看里面装了什么，点一台设备能高亮它的所有连线。

验收：200 个机柜 + 3000 台设备的场景，交互帧率 ≥ 30fps，点选延迟 < 100ms。

## 3. 业务现状与领域模型（反向工程结论）

这一节是需求的技术地基。**所有数字都是实测的**，可直接作为开发阶段的验收基线。

### 3.1 机房空间模型

从 `机房平面图` sheet 反解出的真实几何：

- **2 个房间**：404 机房（丝路信息港业务，4kW/柜，总 181 架）、403 机房（4kW/柜，总 181 架）
- **14 条通道**：404 侧为 八/九/十/十一/十二/十三/十四通道（编号 8~14），403 侧为 一/二/三/四/五/六/七通道（编号 1~7）
- **每条通道两侧各一排机柜**，柜号 1~27（部分通道 1~25，因空调位占位）
- **柜号排布是镜像的**：通道 N 侧，一侧柜号自左向右递增（1,2,3...），另一侧递减（...27,26,25）。例如通道8 北侧 C3=1,D3=2,E3=3...，南侧 C4=27,D4=26,E4=25...，即 1↔27 相对、2↔26 相对
- **通道内非机柜占位**：`空调`、`柱子`、`空调管道间`、`走道`
- 403 侧柜号整体反向（W3=13 递减到 AL3=1）

**这个镜像关系是整个线长算法的关键**：两台机器是否"面对面"取决于它们在哪一侧，而不只是柜号差。

### 3.2 机柜与设备模型

**机柜**
- 标准 42U，宽 0.6m（0.6 这个数字来自 `布线表` R 列公式 `=P2*0.6*120%`，是实测的柜间距常量）
- 有功率预算：4kW/柜
- 有机柜号、所属通道（房间隐含在通道编号里）

**设备摆放**

- `U位` 字段是**字符串**，实测共 **13 种形态**，不能直接当数字用：
  - 单 U：`40U`（3034 行）、`37U`（2116 行）、`34U`（198 行）、`38U`（2 行）
  - 区间：`3-4U`（634）、`7-8U`（622）、`11-12U`（601）、`15-16U`（601）、`19-20U`（599）、`23-24U`（563）、`27-28U`（476）、`31-32U`（476）、`3-12U`（304，10U 高的框式设备）
  - → 系统内部必须拆成 `u_start` / `u_end` 两个整数，并保留 `u_raw` 原值溯源

**设备实例模型（v1.1 重要修正）**

v1.0 曾写"128 个设备实例、位置完全一致、0 冲突"，**这是错误的**。二次实测发现：

- 布线表「本端设备」列填的是**设备型号名**，只有 **28 种取值**（如"业务接入交换机 1"出现在 30 个不同位置），**不是设备实例名**
- 真正的实例身份只能靠 `(型号名, 通道, 机柜, U位)` 四元组反推 → **836 个实例**（型号名**原样**比较）/ **834 个**（型号名去空格归一化后）。另有一个独立口径：`(通道,机柜,U位)` 三元组去重 = **824 个物理位置**。**四个数都对，统计口径不同**，见 00 号基线 §2 的四口径对照表
- 去掉 U 位只按 `(型号名, 通道, 机柜)` 统计则只有 **262 个** —— 差 3 倍，说明同柜同型号确实有多台
- **数据并不一致，存在真实冲突**：
  - 同机柜内 **13 对 U 位区间物理重叠**（型号名原样口径；**去空格归一化后是 11 对**，差 2 对来自 `业务接入交换机 1`/`业务接入交换机1` 名称变体，见 00 号基线 §2），如 ch1 rack1 的"业务核心交换机@3-12U"与"防火墙1@3-4U"
  - 同一型号在同一机柜被记为两个不同 U 位（业务接入交换机 2 在 ch1 rack20 与 ch1 rack7 同时是 34U 和 37U）
  - → **U 位不能作为唯一键的一部分**，`DeviceInstance` 必须有自己的系统生成 `id`

**因此三层模型必须拆开（不能合并）**：

```
DeviceModel（型号，28 个）
  ├─ name                型号名，如"业务接入交换机 1"
  ├─ port_panel_template 端口面板模板 → 决定该型号有几个什么类型的端口
  └─ 实例化 ↓
DeviceInstance（实体设备，836 个原样 / 834 个归一化 / 824 个物理位置）
  ├─ id                  系统生成，如 dev_0001（**业务主键**）
  ├─ model_id            → DeviceModel
  ├─ rack_id             → Rack
  ├─ u_start / u_end     整数 U 位（解析自 u_raw）
  ├─ u_raw               原始字符串（"3-12U"），保留溯源
  └─ serial_no / asset_no 可选（资产号，实施后回填）
       └─ 实例化 ↓
Port（端口，10203 个）
  ├─ id, instance_id, name（物理名如 "GE1/0/1"）, alias（显示别名如 "千兆1"）
  └─ speed / media / status
```

**关键约束（架构必须遵守）**：
1. `DeviceModel` 与 `DeviceInstance` **必须分表**。一个型号的多个实例共享同一端口面板模板，只在实例上存位置。
2. 导入时 U 位重叠**不能阻断**（源数据本来就这么脏），转为「待人工确认」告警队列。
3. 设备名称比对**必须去空格归一化**（`re.sub(r"\s+","",name)`），否则 28 种名字会被当成独立型号。
4. **必须建别名映射表** `NameAlias(source_system, raw_name, canonical_model_id)`：布线表叫 `业务接入交换机 1`、U 位点位图叫 `计算接入交换机(业务)`，两套命名**无机械映射规则**，只能人工维护。
5. 机柜也有三套标识（`rackN` / `A模组-<通道>-<柜号>` / 平面图列坐标），`Rack` 实体必须同时容纳：`aisle_no`、`side`、`seq_no`、`col_index`、`row_index`、`display_name`。**`col_index` / `row_index` 不可省**，N/O 线长公式必须用它们。

**实测的设备类型与规模**（`布线表` 本端设备 top）：
| 设备类型 | 实例数 | 每实例端口数范围 |
|---|---|---|
| 业务核心交换机 | 2 | 86 ~ 89 |
| 存储核心交换机 | 2 | 64 ~ 67 |
| 计算接入交换机(业务) | 26 | 24 ~ 49 |
| 计算接入交换机(存储) | 26 | 24 ~ 49 |
| 计算带内交换机 | 26 | 24 ~ 49 |
| 计算带外交换机 | 13 | 24 ~ 46 |
| 存储接入交换机 | 6 | 36 ~ 43 |
| 存储带内交换机 | 6 | 36 ~ 43 |
| 存储带外交换机 | 3 | 36 ~ 40 |

### 3.4 线缆模型与**线长计算公式**（核心资产）

`布线表` 的 P/R/S/T 四列是**活公式**，这是整个系统最有价值的规则沉淀，必须完整继承：

```excel
P2 (机柜数量) = N2 + O2
   其中 N = 跨机柜（等效柜宽常量），O = 间隔机柜

R2 (柜间线缆) = P2 * 0.6 * 120%
   → 柜间距 0.6m，含 20% 余量 → 等效系数 0.72 m/柜

S2 (线缆2) = R2 + Q2
   其中 Q = 机内线缆（机柜内跳线长度）

T2 (线缆长度1，计算值) = IFS(
   S2<=5   → 5,
   S2<=6   → 7,
   S2=7    → 7,      ← 原有 bug：6 < S2 < 7 落空，会掉到下一档 10
   S2<=8.5 → 10,
   S2<=13  → 15,
   S2<=17.5→ 20,
   S2<=22  → 25,
   S2<=27  → 30,
   S2<=32  → 35,
   S2<=37  → 40
)

U2 (线缆长度，最终核定值) = 人工填写
```

> **原公式存在隐藏 bug（必须在系统实现时修正）**：`S2<=6 → 7` 与 `S2=7 → 7` 之间留了 `(6, 7)` 的开区间。
> 任何落在 6 < S ≤ 7 之间（不含 7）的值都不会命中，直接掉到 `S2<=8.5 → 10`，比预期多一档。
> 系统实现时应改为连续区间：`S2<=7 → 7`。**但历史数据是按原公式算的，回归测试时需注意这一差异**，
> 并保留"旧公式复现模式"用于验证历史 Excel 的一致性。

**采购档位表**（从 T 列公式与 `首期耗材需求清单` 交叉验证）：`5, 7, 10, 15, 20, 25, 30, 35, 40`（米，9 档）
- **采购汇总只有 8 档**：`35` 不单独采购，合并到 `40`（实测 `首期耗材需求清单` 里 LC-LC / MPO / RJ45 各 8 个长度档位）
- 另有 `30` 档：T 公式算出 30 但采购按 30 或 25 均有出现，说明采购端还有一次人工归并

**实测参数值与反解结果**（详细推导见 `docs/architecture/01-线长算法反解报告.md` v1.2）

> **关键前提：N 和 O 在源 Excel 里全是人手填写的字面值，零公式。** 实测：N 列 641 个字面值、0 公式；O 列 640 个字面值、0 公式。只有 P/R/S/T 是活公式（各 636 个）。这解释了为什么吻合率会随行段漂移——不同人、不同批次填的。

**N（跨机柜）—— 已完全反解，公式确定**

```
d = |row_of(通道a, 侧a) - row_of(通道b, 侧b)|   # 平面图行号差
N = 0        if d == 0
N = 4*d + 4  if d > 0
```

- 命中率 **627 / 636 = 98.6%**，剩余 9 条经逐行核实全部是源数据人工填错 → **N 可 100% 全自动计算**
- 几何来源：403 房间通道 k∈[1,7] → 北侧行 `3+2(k-1)`、南侧行 `4+2(k-1)`；404 房间通道 k∈[8,14] → 北侧行 `3+2(k-8)`、南侧行 `4+2(k-8)`
- 物理含义：`4*d` 是跨 d 条通道的机柜宽度当量，`+4` 是两侧各 2 柜的端部余量

**O（间隔机柜）—— 分层公式，整体 91.8%**

O 不是单一公式，取决于两柜的空间关系。**核心物理洞察：机房走线架只架在每排端部，不在通道中间。**

```python
# A 类：同排（两柜在同一平面图行、隔通道面对面）→ 直接横穿通道
O = abs(col_of(rack_a) - col_of(rack_b))

# B 类（同通道跨侧，相邻两行）与 C 类（跨通道）
# → 必须先沿本排走到排端走线架入口，再从对端排端入口折返
O = (CMAX[room_a] - col_of(rack_a)) + (CMAX[room_b] - col_of(rack_b)) + 1
# CMAX[403] = 38, CMAX[404] = 18   ← 该房间机柜列坐标最大值，即排端入口列
```

| 类别 | 样本数 | 命中数 | 命中率 |
|---|---|---|---|
| A 同排 | 496 | 462 | **93.1%** |
| B 同通道跨侧 | 100 | 98 | **98.0%** |
| C 跨通道 | 40 | 24 | 60.0% |
| **合计** | **636** | **584** | **91.8%** |

- 排除 N 填错的行后（627 行）：A 93.9%、**B 100.0%**、C 64.9%、合计 93.1%
- **N 与 O 错误强相关**：N正确&O正确 584 行 / N正确&O错误 43 行 / **N错误&O正确 0 行** / N错误&O错误 9 行 → **"N 错则 O 必错"**，证明二者出自同一人的同一次空间关系判断。52 处异常（8.2%）全部是人工填表错误
- **已证伪的模型（不要再试）**：`|柜号差|` 36.0%、`|柜号差|+1` 7.4%、`ceil(|Δcol|/5)` 30.7%、环形/蛇形绕行 A 类 45.6% B 类 8.0%、`|Δcol|+N` 等组合 77.2%
- **柜号镜像陷阱**：403 房间通道两侧柜号反向（1↔27 面对面、2↔26），按柜号差算距离会大错

**O 的反解对产品的指令**：
1. `CMAX`（排端走线架入口列）必须建模为**一等公民**（`Rack`/`Room` 上的字段），不能硬编码
2. 置信度分级：A 类高、B 类极高、C 类中（C 类 16 个例外集中在管理核心交换机、业务核心交换机，属人工判断差异）→ C 类结果的 UI 上必须标记"建议人工复核"
3. 走线架真实路径图模型列为 P1 增强项（当前只有端部入口假设，没有中间桥架数据）

**Q（机内线缆）**：实测只有 `5` 和 `7` 两个值，且强绑定线缆类型，无例外：

| 线缆类型 | 实测分布 | 规则 |
|---|---|---|
| MPO | `{5: 84, 7: 4}` | 默认 5 |
| LC-LC | `{5: 290, 7: 4}` | 默认 5 |
| RJ45 | `{7: 254}` | **固定 7**（硬规则，零例外） |

**人工核定 U 与计算值 T 的差异分布**（636 条跨机柜记录）：

| T（计算） | U（核定） | 条数 | 说明 |

### 3.4.1 两种长度口径并存（v1.2 新增，v1.3 更正为两种，架构级约束）

> **⚠️ 更正（v1.3）**：早期版本曾把这 9 行 U 空的行列为"第 3 种群：无长度"。**这是错的** —— 那 9 行（r707-709/715-717/723-725）的 `P=5/4/3`、`Q=5`、`R=3.6/2.88/2.16`、`S=8.6/7.88/7.16`、`T=15/10/10` **全部有值**，它们属于种群 1，只是**尚未核定 U**。`636 + 4477 = 5113` 已完全闭合，不存在第三种群。
>
> 这 9 行反而是一个**极有价值的状态样本**：「已算出 T、未核定 U」正是**任何新建项目在人工核定之前的天然状态**。产品必须把这个状态做成一等公民（`U = NULL` 且 `status = 'CALCULATED_PENDING_APPROVAL'`），而不是当成"缺数据"报错。种群 2 里那 2 行 `T = "待定"`（文本塞进数值列）才是真正的脏数据样本。

**这是架构级事实，不是脏数据**：种群 2 的 N/O/P 整条公式链被系统性绕过。若系统只提供「计算值 T + 人工微调 U」一条路径，用户导入存量项目后会看到 **88% 的行全部标红"计算值与人工值不符"**，产品直接不可用。

**因此长度必须做成「策略 + 行级溯源」，而不是"计算层 + 核定层"两层**：

| 策略 | 取值来源 | 适用场景 | 是否参与"与计算值不符"告警 |
|---|---|---|---|
| `GEOMETRIC` | `calc_len_t = IFS(0.72×(N+O) + Q)` | 需严格按设计院公式口径交付、历史回归比对 | 是 |
| `EMPIRICAL` | `(空间关系类, 线缆类型, 物理路径距离) → 长度` 经验表 | **新项目推荐默认** | 是（对经验表建议值） |
| `MANUAL` | 用户手填 | C 类跨通道、MPO 主干、核心→接入等高频错误场景 | 否 |
| `IMPORTED` | 导入 Excel 原值，**保留原值不被重算覆盖** | **存量项目迁移（那 4477 行）** | **否** ← 否则 4477 行全红 |

**四条不可协商**：①`calc_len_t` **任何策略下都恒算**，它是审计与迁移的唯一对比基准；②`IMPORTED` 行不得被重算覆盖；③策略可逐行切换，切换写审计日志并保留旧值；④策略是**行级属性**，同一项目内可混用（存量迁移后新规划走 `GEOMETRIC`）。

**经验表口径实测（LOO 留一交叉验证 = 拿走该行自身数据后预测，模拟"遇到没见过的新行"）**：

| 模型 | LOO 命中率 |
|---|---|
| **`(空间关系类, 线缆类型, 物理路径距离)` 经验表** | **87.11%** ✅ |

| **原公式 `T = IFS(0.72P + Q)` 外推到全量 5104 行** | **61.66%** ❌ |

`path`（物理路径距离，列坐标单位）：A 同类同排 `path = abs(col_a - col_b)`；B/C 类 `path = (CMAX[room_a]−col_a) + (CMAX[room_b]−col_b) + 1`。

|---|---|---|
| **IFS 逐字**（`S≤6→7`、`S==7→7`、`S≤8.5→10`） | **636/636 = 100.00%** | 0 ✅ |
| IFS 连续化（`S==7` 改 `S<=7`） | 587/636 = 92.30% | **49**（S 恒为 6.44，被 `(6,7)` 缝隙吃掉） |
| 档位表 ladder_round | 424/636 = 66.67% | **212** ❌ |

> 即 §3.4 中"应改为连续区间 `S2<=7 → 7`"的建议**成立但必须做成开关**：默认 `ifs_compat`（逐字复刻，保证 AC-1 达标），连续化作为可选模式并显式告知 49 行差异。这 49 行是"多买一档线"的真实损失，可作为体检项报出。


### 3.5 连线表的 5 种版式（导入功能的核心难点）

| # | 来源 | 列数 | 版式特征 |
|---|---|---|---|
| 1 | V13 `布线表` | 25 | 本端 6 列 + 对端 6 列 + 13 列计算/属性。单行表达一条双向连线 |
| 2 | V13 `连线表(不含长度)` | 13 | 版式 1 去掉计算列，但**行数不一致**（5307 vs 5127），说明两份拷贝已经不同步 |
| 3 | 政务外网区各 sheet | 9 | `本端机柜\|本端位置\|本端设备\|接口\|对端设备\|对端端口\|对端机柜\|对端位置\|线缆类型`。机柜用 `A-7-01` 三级编码，U 位用 `4U-15U` 区间 |
| 4 | 11+12冷通道 `连线表` | 24（双栏） | **横向成对排布**：左栏是设备A，右栏是设备B，中间靠行对齐。行首有 3 行标题描述机柜信息 |
| 5 | 11+12冷通道 `核心交换机` | 9 | `位置\|本端设备名称\|端口号\|本端标签\|对端标签\|对端设备名称\|接口类型\|长度`，标签格式 `11A14-16U HLW-YWHX01(SW) 40GE2/0/1` |

**此外还有特殊行**（必须能识别并跳过或特殊处理）：
- 政务外网各 sheet 里，每个交换机的第一个端口行是 `GL`（管理口），无对端
- 有大量空对端行（表示该端口预留未接）
- `分线` sheet 里有 `Eth5 … Eth24` 这种省略行

> **需求结论**：导入器必须是**「版式模板 + 列名别名映射」驱动**的，不能硬编码。每个模板定义：表头识别规则、列→字段映射、表头所在行、数据起始行、多栏偏移。用户能保存自定义模板。

### 3.6 耗材与模块模型

`首期耗材需求清单` 的结构揭示了耗材汇总逻辑：

**线缆需求**（类型 × 长度 二维表）
- 需求数量 = 该类型该长度的连线条数
- 采购数量 = 需求 × 1.3（+30% 冗余）
- 实测：LC-LC 有 5/7/10/15/20/25/30/40 八个档位；MPO 同；RJ45 同

**模块需求**
- 分「本端需求数量」「对端需求数量」「实际需求数量 = 本端 + 对端」「采购数量」
- 实测：100G-SR4 本端90/对端88/合计178/采购200；10G-SR 112/28/140/324；25G-SR 85/15/100/156；光转电 12/0/12/15
- 特殊规则：`设备自带` 模块不计入需求（实测对端有 181 处"设备自带"）

**逻辑网络 ↔ 物理网卡映射**（`服务器接线示意` sheet）：
- 5 个物理网络：`物理网1-带外管理网`、`物理网2-带内管理网络`、`物理网3-控制网`、`物理网4-业务网`、`物理网5-存储网`

> **需求结论**：需要「逻辑网络」实体 + 「网卡端口 → 逻辑网络」映射规则。这是自动生成布线表的**输入之一**——知道一个端口属于哪个逻辑网络，才能推导它该连到哪类交换机。

### 3.8 设备型号库

从 `首期设备清单`（22 类设备）可提炼出型号库的字段需求：

- 类型、名称、配置描述（长文本，含端口板卡明细）、数量、套餐、使用规划、上联设备
- **关键**：配置描述里藏着端口信息，如「36 端口 100GE 以太网光接口板 × 3，48 端口 25GE 以太网光接口板 × 1」→ 可解析出 108 个 100G 口 + 48 个 25G 口
- 服务器型号更细：`5222C（32核，2.6GHz）× 2，32G × 8，...，2个25Gbps网口和2个1Gbps网口`

> **需求结论**：型号库要支持"端口模板"——一个设备型号定义一组端口（板卡 × 数量），实例化时自动展开成具体端口列表。这是自动生成布线表的前提。

## 5. 数据需求

### 5.1 核心实体清单

```
Project（项目）
 └─ Room（机房）
     └─ Aisle（通道）
         └─ Rack（机柜）
             └─ RackMount（上架记录）─→ DeviceInstance（设备实例）
                                          └─ Port（端口）
DeviceModel（设备型号）
 └─ PortTemplate（端口模板）
Cable（连线）─→ Port（本端）、Port（对端）
CableSpec（线缆规格）
TransceiverModel（光模块型号）
LogicalNetwork（逻辑网络）
CableLengthRule（线长规则）
ImportTemplate（导入模板）
Version（版本快照）
AuditLog（审计日志）
```

### 5.2 关键字段与约束

**Rack（机柜）**
- `rack_no` 柜号（int 或 string 编码，如 `A-7-01`）
- `aisle_id` 所属通道
- `side` 侧别（A/B，或 N/S）— **线长算法必需**
- `position_index` 通道内的列顺序索引 — **线长算法必需**
- `total_u` 默认 42
- `width_m` 默认 0.6
- `power_budget_kw` 默认 4

**RackMount（上架）**
- `rack_id`, `device_instance_id`, `start_u`, `end_u`（end_u - start_u + 1 = U 高）
- 约束：同一机柜内 U 区间不重叠

**Port（端口）**
- `device_instance_id`
- `physical_name`（`GE1/0/24` / `千兆1` / `IPMI`）
- `display_name`
- `port_type`（electrical / optical）
- `speed_mbps`（1000 / 10000 / 25000 / 40000 / 100000）
- `connector`（RJ45 / LC / MPO）
- `breakout_parent_id`（拆分父端口）
- `logical_network_id`
- `status`
- 约束：`(device_instance_id, physical_name)` 唯一

**Cable（连线）**
- `a_port_id`, `z_port_id`（唯一约束：一个 port 只能有一条 cable）
- `cable_type`（RJ45 / LC-LC / MPO）
- `cross_rack_n`, `gap_rack_o`, `rack_count_p`（自动算）
- `in_rack_q`, `inter_rack_r`, `total_s`, `calc_len_t`, `approved_len_u`
- `a_module`, `z_module`
- `approved_by`, `approved_at`, `approve_reason`（人工调整记录）
- `status`, `remark`

**CableLengthRule（线长规则，可配置）**
- `rack_spacing_m` = 0.6
- `slack_ratio` = 1.2
- `ladder` = [5, 7, 10, 15, 20, 25, 30, 35, 40]
- `in_rack_len_by_type` = {RJ45: 7, LC-LC: 5, MPO: 5}（可覆盖）
- `cross_aisle_n_map`（通道对 → N 值映射表）

## 附录 B：术语表

| 术语 | 含义 |
|---|---|
| 通道 / 冷通道 | 机房内两排机柜之间的走道，机柜面对面排列 |
| U | 机柜高度单位，1U = 44.45mm，标准机柜 42U |
| 跨机柜 N | 布线表中的等效柜宽常量，与通道对相关 |
| 间隔机柜 O | 布线表中两机柜之间隔的柜数 |
| 机内线缆 Q | 机柜内部跳线长度 |
| 柜间线缆 R | 跨机柜部分的线缆长度 = 机柜数量 × 0.6 × 1.2 |
| MPO | 多芯光纤连接器，用于 40G/100G 并行传输 |
| LC-LC | 双芯光纤跳线，用于 10G/25G |
| RJ45 | 标准网线接口 |
| Breakout | 高速端口拆分为多个低速端口，如 1×100G → 4×25G |
| ToR | Top of Rack，柜顶接入交换机 |
