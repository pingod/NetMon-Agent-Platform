## 1. 产品定位与一句话叙事

### 1.1 一句话

> **你的 Excel 不用扔。我们让它会算线长、会查冲突、会一键出布线表和耗材清单，改完还能导回去。**
> [原句出自 R04 §6.3]

再短一版，用于口头介绍：

> **给 IDC 交付团队用的"Excel 增强器"：一份数据源，同时出布线表、U 位图、耗材单，还能往返不丢东西。**

### 1.2 三句话讲清楚我们在解决什么

| # | 事实 | 出处 |
|---|---|---|
| 1 | 客户已经把这件事在 Excel 里做到了 **V13、25 列 × 5113 条连线、40 天迭代 6 个版本**，说明工作方式不需要教育，痛点是"表格撑不住了" | REQ §1.1、ARCH00 §2 |
| 2 | 那份表里 **P/R/S/T 四列是活公式**（各 636 个公式单元格），而 **N/O/Q/U 四列全是手工字面值**（0 个公式）——**人工在算一个本可以算的东西** | RPT §1 |
| 3 | 全市场 13 个 DCIM 产品里，**"布线表 / 线长"一列没有任何一个干净的 ✔ 且不依赖硬件**；而唯一免费的同类竞品 AutoLink 走的是"模板生成"路线，**接不住存量 Excel** | R04 §4、§6.2 |

### 1.3 电梯陈述（30 秒版）

> 甘肃信息港这个项目，实施团队用 Excel 做了 13 版、5113 行布线表，40 天改了 6 稿，同一份数据在三个 sheet 里各维护一遍，还靠 `（旧）` 文件名做版本管理。我们做的是一个**离线单机工具**：把这份 Excel 完整吃进来，用机房的真实几何位置把线长算出来（不是查表，是按机柜在哪、隔几个柜算），把冲突查出来，一键出交付物，施工队在现场改完还能导回来。**不是取代 Excel，是让 Excel 会算。**

### 1.4 电梯陈述（3 分钟版，销售/汇报用）

1. **现状**：客户当前交付物是 Excel。这不是落后，是刚需——施工队拿的就是那张表，甲方归档的也是那张表（R04 结论 3）。
2. **痛点**：一旦行数上到 5000 量级、版本迭代到 6 稿，Excel 就变成"人工数据库"，必然分裂：布线表 5113 条 vs 连线表 5307 行，按共同列比对**完全不重叠**（REQ §3.1）；同一型号有两种写法（`带外交换机1` / `带外交换机 1`）。
3. **我们能做而 Excel 做不到的四件事**：①按几何位置**算**线长（不用人数格子）；②**查**出表里的错（实测 52 处 N/O 填错 + 13 对 U 位物理重叠）；③一份数据**同时**出布线表 / U 位图 / 耗材单；④**往返保真**——导出给现场改，导回来不丢列、不丢公式、能 diff。
4. **代价**：一套系统买断，万元级，离线单机，不改变任何现有工作习惯（输入输出都是 Excel）。

### 1.5 我们不是什么（反对句，必须在每次对外沟通中主动说）

| # | 我们不是 | 理由 / 出处 |
|---|---|---|
| A1 | **不是 DCIM 平台** | 商用 DCIM 主战场是运维期监控与容量，不是交付期布线表（R04 结论 1）。我们不做动环、不做 PUE、不做告警 |
| A2 | **不是 NetBox 套壳 / 不是二开插件** | 把 5113 行灌进 NetBox，25 列里 6 列（14~19）**无处安放**，3 列只能存不能算，且导不出原表（R01 判据一/三）。等于把 Excel 的痛点搬进 Web |
| A3 | **不是 AutoLink 的替代品** | AutoLink 起点是"GPU 规模参数 + 模板"，客户是规划院做**售前方案**；我们起点是"已有 Excel + 真实机柜位置"，客户是实施团队做**施工文档**。不同工位（R04 §6.2） |
| A4 | **不是 3D 可视化产品** | 最强反证：Pathfinder 是布线能力最完整的商业产品，功能全表里 "3D" 出现 **0 次**，却把跳线表 / 线长 / 端口矩阵做到了最好（R04 §2.8、§5.3） |
| A5 | **不是 IPAM、不是 CMDB、不是工单系统** | 客户 `IP地址段规划` 只有 11 行网段级（REQ §3.7），不需要逐地址分配；工单/巡检属运维期，用户明确"现在不做"（REQ §4.10） |
| A6 | **不是 CAD / 不是 BIM** | 客户平面图是 **40 列 × 16 行的文本网格**，是格子不是矢量图（R04 P1-6）。做到"网格化平面图 + 柜号 + 通道归属"即可 |

### 1.6 与 AutoLink 的正面切割（这是最容易被客户拿来比价的对手）

| 维度 | AIDC AutoLink（MIT，免费） | 本产品 |
|---|---|---|
| 起点 | 规模参数（GPU 64~2048）+ 模板 | **已有 Excel / 已有设备清单** |
| 目标客户 | 智算中心规划院做**售前方案** | IDC 实施交付团队做**施工文档** |
| 拓扑来源 | 算法生成（Fat-Tree / Rail-Optimized） | **人工给定 + 系统校验** |
| 机柜 | 42U/49U 参数化，`rack_layout.json` 自动生成 | 真实柜号、通道、侧别、U 位、镜像排布 |
| 布线表 | "布线指导表"，由拓扑推导 | "施工布线表"，由**真实几何 + 端口**推导 |
| 设备库 | 131 款 GPU 精选库 | 客户实测 28 种型号（含鲲鹏 920 / 海光 7390H / 密评设备） |
| 输出 | 布线表 + BOM + 9 章 PDF | 25 列布线表 + U 位图 + 耗材单 + 体检报告 |
| 强项 | 生成速度快、23 条校验、完全离线 | **保真、可回写、可 diff、异构设备、能查错** |
| 定价 | 免费 | 万元级买断 |

> **应对客户"AutoLink 免费就有"的标准话术**："AutoLink 是从零生成一套**新**方案，它假设你还没有方案。你的方案已经在 Excel 里了——5113 行、改了 6 版、还有 52 处人工错误没人发现。AutoLink 帮不了你，**它不会读你的表，也不会告诉你表里哪里错了**。它是 MIT，你可以自己改；但你需要的不是改代码，是明天就能出施工表。" [依据：R04 §6.2；差异化能力来自 REQ §4.5b 数据体检 + RPT §4.3「偏差全为源数据错误」]

### 1.7 定位成立的前提条件（诚实声明）

本定位在下列任一条件被推翻时**需要重新评估**：

| # | 前提 | 若不成立会怎样 |
|---|---|---|
| P1 | 客户继续把 **Excel 作为最终交付物** | 若甲方改为"系统里看 + PDF 归档"，则 H1（双向保真）价值归零，产品退化为普通表格工具 |
| P2 | 线长仍然是**采购/施工的关键字段** | 若现场改为"估一堆、按需领用"，则 H2 归零 |
| P3 | 客户的机房布局仍然是"**每排端部走线架**" | 若换机房后走线架在通道中间，N/O 公式需重标定（见 §10 R1） |
| P4 | 客户愿意为"**少改几版**"付钱 | 若客户认为"多改几版无所谓"，则价值主张只剩"查错"，定价需下调 |

## 2. 目标用户与决策链

### 2.1 五类角色：谁关心什么、谁付钱、谁用

| 角色 | 在项目里的位置 | 真正关心的事 | 会不会天天用 | 对产品的态度 |
|---|---|---|---|---|
| **设计院工程师** | 出图出表的上游 | 「我填的长度不要被人改错」；表格格式要能直接交 | 会用（导入/导出为主） | **潜在抵制**：系统算的线长与他的经验值不一致时，他会觉得"机器不懂现场" |
| **实施方项目经理** | 交付主体，**最可能的付费方** | 工期、返工、耗材买多买少、验收能不能一次过 | 每天看汇总，不一定每天编辑 | **最积极**：返工和超采都是他的成本 |
| **施工队长 / 现场工程师** | 按表干活的人 | 表要能打印、要按机柜分组、标签要对、线长要够长（宁长勿短） | 每天用（打印 + 核对） | **只关心输出物**：系统长什么样无所谓，出来的 PDF/Excel 好不好用才要紧 |
| **甲方监理** | 验收签字方 | 数据是否自洽、能否追溯、有无审计记录 | 偶尔查（只读） | 中性偏正面：审计日志与体检报告是他的抓手 |
| **甲方审计 / 等保测评** | 合规关口 | 账号、权限、审计日志、数据备份 | 不直接用，只看材料 | **一票否决权**：没有账号体系与审计日志，产品进不了政务云 |

> [角色定义依据 REQ §2.1；等保要求依据 R04 §7.1、REQ NFR-9]

### 2.2 决策链（钱是怎么花的）

| 环节（谁发现痛点 → 谁评估 → 谁签字 → 谁付钱 → 谁天天用：施工队长（返工抱怨）→ 实施方 PM（算 ROI）→ 甲方监理（看合规）→ 实施方/甲方（项目预算）→ 规划+施工（Excel）） | 关键判断 | 对我们的含义 |
|---|---|---|
| 触发 | 出现一次"线买少了 / 买多了 / 返工" | 销售切入点应是**事故复盘**，不是功能演示 |
| 评估 | 能否在**本期项目结束前**产生价值 | 必须能"导入现有 V13 立刻出结果"，不能要求先建项目（见 §4 数据体检前置） |
| 签字 | 监理看的是"数据可追溯" | 审计日志与体检报告要能**单独打印成一份材料** |
| 付钱 | 项目制预算，**一次性入账** | 只能买断，不能订阅（见 §8.3） |
| 使用 | 施工队长不接受学习成本 | 输出必须仍是 Excel/PDF；系统界面只给 2~3 个人用 |

### 2.3 三个核心 Persona（从 US-1~US-7 归并）

| Persona | 老周 — IDC 规划工程师（**主用户，占 70% 使用时长**） | 小李 — 实施交付工程师 / 施工队长（次用户，**决定口碑**） | 王经理 — 实施方项目经理 / 采购（**付费决策人**） |
|---|---|---|---|
| 对应 US | US-1 建机房、US-2 批量上架、US-3 出布线表、US-5 改布局重算 | US-4 导入历史表、US-6 生成施工交付物 | US-6 的耗材部分、AC-5 |
| 现状 | 在 Excel 画 305 行 × 84 列格子图、500 个合并单元格硬画机柜阵列（R04 P0-1）；**一天的样子**：早上改一个机柜位置 → 中午发现长度全错 → 下午手工重算 636 行 → 晚上发现另一份连线表没同步 | 拿一张 5113 行的总表去现场，靠 Ctrl+F 找自己负责的机柜 | 拿 `首期耗材需求清单` 手工汇总，凭经验加冗余下单 |
| 他要的三件事 | 改一处全联动、线长自动对、别再维护两份表 | 按机柜分组打印、标签清单能直接给标签机、线长宁长勿短 | 一键出采购量、能对比到货、漏项能被提示 |

| 成功标准 | 一版布线表 3.8 人天 [假设] → 0.5 人天 [假设] | 现场不必回办公室问"这根线到底多长" | 采购量/需求量稳定在 1.3±0.05 |

### 3.2b 两个最硬的数字（比"省多少人天"更有冲击力，对外沟通优先用这两句）

> **① 布线表 5113 行 → 填约 30 行。** 用户不再逐行填表，而是用约 30 行 YAML 声明"哪些节点归哪台交换机、每台交换机的起始端口从哪算"，系统据此生成全表。依据：**ARCH03 §3.2、§9.1**（三层生成模型：设备-网络角色映射 64 条 + 节点排序 `rack asc, u_start asc` + 端口分配 `port = base + i`）。

> **② 端口号人工排 3850 个 → 0 个。** 交换机侧端口号 = 组内位次 + `base`，实测 **3850/3850 = 100.00%** 命中；U 位槽位相位 `slot_i ≡ (i+φ) mod 8` 实测 **112/112 组 = 100%**，且 φ 是首节点 slot 的派生量、零人工配置。依据：**ARCH03 §4、§5.4**。
>
> **③（配套，口径已修正）25 列中 22 列可全自动 / 1 列半自动（模块）/ 1 列人工或经验表建议（核定长度）/ 1 列自由文本（备注）。** 依据 §4.2 覆盖率表；**模块列不能算"全自动"**，原因见 §4.2b。
>
> **④ 存量 5104 行要判断长度：约 87% 由系统给可信建议，约 13% 强制人工。** 实测：**87.6% 的行（4477/5113）历史上根本没走公式链，是人工从零填的**；系统用经验表对这些行的留一交叉验证命中率 **87.11%**，而原公式只有 **61.66%**。C 类跨通道（260 行）与 MPO（353 行）覆盖率仅 37.5%~69.6%，**明确强制人工**。依据：**ARCH §4.1A、RPT §5A**；分档见 **§4.5b**。

### 3.3 分期实施：被 Excel 吃掉的那 91.2%（**新增核心发现**）

**大多数人（包括此前的需求文档）把这份 Excel 理解成"同一份数据的 4 个视图"。实测不是。它是 4 个不同"批次/范围"的数据块混在一个文件里：**

| 数据块 | 实际覆盖范围 | 数量 | 占全量 |
|---|---|---|---|
| `布线表` | **全量完整规划** | 5113 条连线 / 824 个设备物理位置 | **100%** |
| `首期设备清单` | **仅首期采购批次** | 84 台（22 个型号行 `数量` 求和） | **10.2%** |
| `首期耗材需求清单` | **仅首期采购批次** | 450 条线缆（`备注1="首期"`） | **8.8%** |
| `连线表(不含长度)` | 声称与布线表同源 | 5110 条 | 去重后与布线表**完全不重叠** |

**证据链（三层印证同一结论）**：

1. `首期耗材需求清单` 的 C 列公式是 `=COUNTIFS(布线表!X:X,"首期",布线表!M:M,A3,布线表!U:U,B3)` —— **它自己就带了"首期"这个过滤条件**，说明汇总范围本来就不是全表。
2. `布线表` 里 `备注1="首期"` 全表 **450 行**（其中 446 行在 5113 条有效连线内、4 行落在 14 行残留行里），与耗材表统计出的 450 条**完全吻合** —— 这证明"备注1"就是**批次标记字段**，不是备注。
3. `首期设备清单` 22 个型号行的数量求和 = **84**，而布线表里的设备物理位置有 **824** 个 —— 差 9.8 倍。

**三个产品结论，一个比一个重要**：
> **C1 这不是"数据不同步"，是"业务本身分多期"**——项目先买 10% 的设备、8.8% 的线缆，后面分批买，而 Excel **无法表达"这条连线属于第几期"**，只能人工在耗材表里一行行挑 → `phase`（批次/期）必须做成 **DeviceInstance 与 Cable 的一等字段**，不是备注。
> **C2「备注1」这个列名是个陷阱**——它实际承担"批次标记"职责，但叫"备注"，所以没人当它是结构化字段 → 导入时映射为 `phase`（枚举：首期/二期/…），UI 上叫「批次」而不是「备注」，同时保留原值溯源。
> **C3 耗材汇总必须能按期过滤，并能出"三列对照"**：全量需求 / 各期已采购 / 剩余待采购——直接解决"首期耗材表只覆盖 8.8%"，**系统能自动算出"第 N 期需要哪些线缆"** → 耗材模块（M8）升级为按期汇总。

**为什么这条最值钱**：

> 线缆采购是这类项目的**真金白银损失点**。本期实测：需求 450 根 → 声明 +30% → 实采 **829 根 = 1.84 倍**，多下 **244 根**；**同时**又漏掉了整批安全设备线缆（表内自认"未考虑"）。**既多买，又漏买，还只算了 8.8% 的量。**
> 一个 824 台设备的项目，如果按首期比例外推，全量线缆需求约 450 ÷ 8.8% ≈ **5000 根量级**。在这个量级上，采购偏差 10% 就是几百根线的钱。**"系统按期算耗材"是唯一能直接换算成钱的卖点。**

**分期能力的产品级处理（写进路线图）**：

| 阶段 | 做什么 | 为什么放这个阶段 |
|---|---|---|
| **v0.1** | `phase` 字段进数据模型 + 导入时从 `备注1` 映射 + 耗材汇总支持按 phase 过滤 | **模型留位是零成本的**，后补字段要动全部导入器与导出模板。**这是本文唯一一条"强烈建议前移到 MVP"的 P1 能力** |
| **v0.2** | 按期汇总的三列对照视图（全量 / 已采 / 待采）+ 每期的耗材清单导出 | 需要先有稳定的耗材汇总（M8） |
| **v0.3** | 分期规划：新建设备/连线时指定期次；期次之间的依赖（如"二期设备的上联必须先有一期交换机"） | 属规划能力，依赖连接意图 |

### 3.4 收益粗算模型（**全部为假设，需用客户真实工时校准**）

**建模口径**：以"一版完整交付物"为计量单位。一版 = 布线表更新 + U 位图更新 + 耗材单更新 + 两份拷贝对齐。

| 动作 | 工程量（实测） | 单次耗时 [假设] | 折合人天 [假设，8h/人天] |
|---|---|---|---|
| 填 N/O（含查平面图数格子） | 640 行 × 2 字段 | 45 秒/字段 | 16.0 h → **2.0** |
| 画 U 位图（合并单元格） | 951 个合并单元格 | 1.5 人天/版 | **1.5** |
| 汇总耗材（3 类 × 8 档 + 4 模块 + 从 5113 行挑首期 + 核对） | 24 格 + 4 行 | 0.5 人天/版 | **0.5** |
| 两份拷贝对齐 | 5111 条不一致（按业务键比对） | 10 秒/条 | 14.2 h → **1.8** |
| 错误返工（52 处定位 + 复盘） | 52 处 | 20 分钟/处 | 17.3 h → **2.2** |

| 情景 [假设] | 首版 | 每版重做 | 6 版合计 | 说明 |
|---|---|---|---|---|
| **现状（纯 Excel）** | 2.0+1.5+0.5+1.8+2.2 = **8.0 人天** | 1.5+0.5+1.8 = **3.8 人天** | 8.0+5×3.8 = **27.0 人天** | N/O 只在首版填一次，后续微调 |
| **用本产品后** | 导入 0.3 + 体检修正 1.0 + 出表 0.2 = **1.5 人天** | **0.5 人天** | 1.5+5×0.5 = **4.0 人天** | 几何列系统出，U 位图/耗材单一键出 |
| **净节省** | — | — | **≈ 23 人天（约 85%）** | — |

**上面这张表算的是"重做一版"的工时。若换成"存量 5104 行要不要人逐行判长度"，账更硬**：现状是 **5104 行全部人肉凭经验填**（其中 **4477 行 = 87.6%** 历史上连公式链都没走过，见 §4.5b）；用产品后**约 87% 由经验表给建议（LOO 87.11%）、约 13% 强制人工**（C 类 260 行 + MPO 353 行 + 少数高频错设备对）。按 5104 行 × 单行 15 秒 [假设] ≈ **21.3 h ≈ 2.7 人天**可压到 **≈ 0.4 人天**（13% × 2.7）。**这比"省 23 人天"更难被质疑，因为它不依赖任何工时假设，只依赖行数。**

**模型自洽性校验 [假设]**：40 天工期内若老周有 60% 时间花在这张表上 → 40 × 0.6 = **24 人天**，与模型的 27 人天**同量级**，说明假设无系统性偏离。这是本文唯一一次"用总量反推校验"；若实际投入不是 60%，请按比例修正。

**耗材金额的算法（单价缺失，不编造）**：

> 超采根数 = 829 − 585 = **244 根**；漏项 = 安全设备线缆（16 类安全设备中，6 台密评设备已确认需 12 个光转电模块，线缆未计入 [REQ §3.6]）。**节省金额 = 244 × 单价 + 漏项根数 × 单价。单价在现有 5 份文档与源数据中均未出现，需客户提供采购价后代入。** 本文不给金额，避免制造不可回溯的数字。

## 4. MVP 定义（v0.1，可交付验收）

### 4.1 MVP 的一句话定义

> **填约 30 行"接线意图"配置 → 系统自动生成 5113 行布线表（25 列中 22 列全自动） → 只有 2 列需要人点头（核定长度 U、模块确认） → 原样导出 25 列，顺手告诉你表里哪儿错了。**

即：**"声明 → 生成 → 核定 → 导出 → 体检"** 五步闭环。

**这句话与上一版规划的关键差别（必须强调）**：

| | 上一版判断 | 反解后的实际 | 产品含义 |
|---|---|---|---|
| 端口谁排 | "人工给连接意图，系统只是校验" | **交换机侧端口号 = 组内位次 + base，3850/3850 = 100.00%**（ARCH03 C2） | 端口号**完全可自动生成**，人工排 3850 个端口 → **0 个** |
| U 位槽位 | "U 位看起来乱，是脏数据" | **`slot_i ≡ (i+φ) mod 8`，112/112 组 = 100%**，且 φ = 首节点 slot（派生量） | "乱"是**拓扑约束的结果**，不是错；且可做零成本校验器 |
| 服务器口 → 交换机 | "需要人工声明每台机器的上联" | **64 条映射零歧义**（`IPMI`→带外、`千兆1/2`→带内、计算节点 `万兆1..4`→业务/存储双平面分插） | 用户只需声明**节点角色**，不用逐台声明上联 |
| 产品定位 | **"验证已有表格的工具"** | **"能生成表格的工具"** | 价值主张强一个量级：从"帮你查错"变成"帮你干活" |

> 依据 **ARCH03（端口分配算法反解报告）§1、§9.3**、**ARCH00（源数据实测基线）§5**。
> **这一条推翻了本文 v0.9 草稿里"MVP 只做导入+校验、生成能力放 v0.2"的克制判断。** 理由：生成能力的**用户输入成本已经降到约 30 行 YAML**，不做它反而是放弃了最强的卖点。

### 4.2b 为什么模块列只能是"半自动"（实测结论，必须诚实说明）

| 事实（`布线表` 全表统计） | 数值 |
|---|---|
| `本端模块`/`对端模块` 有值的行 | **570 / 5113 = 11.1%**；模块值只有 **6 种**：`一`(472)、`10G-SR`(188)、`100G-SR4`(178)、`设备自带`(178)、`25G-SR`(112)、`光转电`(12) |
| `(设备型号, 端口名) → 模块` 查找表 | 命中率 **97.54%**（328 个权威键）——**查得准**；但**只能覆盖 37.61% 的行**，因为源数据本身只填了 11.1% |
| 纯规则推导（不依赖历史值） | 最高只到 **97.28%**，且有**系统性偏差**：25G 口降速跑 10G、端口名"骗人"的 100G 口、同型号不同批次填不同值 |

**四条结论与产品动作**：①**不能承诺"自动生成模块 BOM"**（承诺了就是给采购埋雷，采购对账不容错）→ MVP 定名 **「模块建议与缺口报告」**；②"建议 + 显式标注覆盖率 + 缺口清单"**比"全自动"更让人信任** → 报告输出三列 `系统建议值` / `依据（查找表/规则/无）` / `覆盖状态（确定/待确认/缺口）`；③**模块漏买是现场停工的直接原因**（线买了、模块没买，设备上不了架）→ 缺口清单（"这 244 个口没有模块归属"）作为独立交付物；④人工确认值要能**回写沉淀**成新查找表条目 → 采纳时写回 `module_lookup`，记录来源项目与确认人。

### 4.3 MVP 做什么（10 项）

### 4.5 关于 AC-1 的表述修正（重要，必须与客户对齐）

REQ 的 AC-1 写的是"`间隔机柜 O` 与人工值一致率 **≥ 95%**"。这个表述**低估了我们的能力，也高估了它**——因为实测分层后是：

| 列 | 实测一致率 | 性质 | MVP 承诺 |
|---|---|---|---|
| N（跨机柜） | **627/636 = 98.6%** | 9 处偏差经逐行复核 **100% 为源数据错误** | 系统 100% 自动算；9 处标 ERROR |
| O（A 类，同排，78% 的行） | **462/496 = 93.1%** | 34 处偏差全部为 ±1 量级人工数格子误差 | 系统给计算值 + WARN 复核提示 |
| O（B 类，同通道跨侧，16% 的行） | **98/100 = 98.0%** | 2 处不符，且该行 N 也同时错 | 系统给计算值 + WARN |
| O（C 类，跨通道，6% 的行） | **24/40 = 60.0%** | **无稳定几何规则** | **强制人工填写，系统只标 INFO，不给"假象"** |
| P / R / S / T | **100%** | 活公式直接复现 | 系统 100% 自动算，不允许人工改 |
| **端口名（本端/对端）** | **3850/3850 = 100.00%** | C2 规则，零例外 | 系统 100% 自动生成 |
| **U 位槽位相位** | **112/112 组 = 100%** | C3 规则，φ 为派生量 | 系统自动校验 |
| U（核定长度，全表 5104 行） | 经验表 **LOO 87.11%**；原公式只有 **61.66%** | 88% 的行历史上就没走公式链（§4.5b） | **按类分档承诺**：A 类 95%+、B 类 78~95%、**C 类与 MPO 不承诺、强制人工**；`IMPORTED` 行保留原值不告警 |

> **建议把 AC-1 改写成五句话**：①N 与 A/B 类 O 由系统计算，与设计院人工值一致率分别为 98.6% / 93.1% / 98.0%，偏差行 100% 经复核为源数据错误，系统可自动定位；②C 类 O（跨通道，6% 的行）**明确不支持自动计算**，强制人工填写；③P/R/S/T/端口名/相位 **100% 复现**，零例外；④**U 列按类分档承诺**：A 类 ≥95%、B 类 78~95%、C 类与 MPO 强制人工（整体经验表 LOO 87.11%，见 §4.5b）；⑤存量导入默认 `IMPORTED` 原值保真，**不因"与计算值不符"告警**。
> **理由**：把"95% 一致率"改成"**100% 正确 + 能查出别人的错**"，是从"我们是个近似算法"变成"我们是个审计 + 生成工具"——这是产品叙事的根本差别。[依据 RPT §4.3 加粗结论、ARCH03 §9.3]

### 4.5b 为什么存量导入必须支持「原值保真」——88% 的行根本没用过公式链

**这会改变 MVP 范围：源表里 87.6% 的行完全绕过公式链，是人工从零填的**（按「P 列是否有值」把 5113 条有效行切成**两个**种群，合计恰好闭合）：

| 种群 | 行数 | 占比 | N/O | P/Q/R/S/T | 长度是怎么来的 |
|---|---|---|---|---|---|
| **1 走公式链** | **636** | 12.4% | 人工填 | 活公式 | 由计算值 T 调整（采纳 352 / 上调 103 / 下调 172） |
| **2 纯人工直填** | **4477** | **87.6%** | **非零 0 行** | **全空**（T 仅 2 行有值） | 人工从零凭经验填 |
| | **合计** | **5113** | 100% | — | — |

> **⚠️ 数字更正（v1.3）**：早期版本列过"第 3 种群：无长度 9 行"，**是统计 bug**。那 9 行（r707-709/715-717/723-725）的 `P/Q/R/S/T` **全部有值**，只是 `U` 未核定 → 属种群 1 的「已算出 T、待核定」状态。`636 + 4477 = 5113` 已闭合。
>
> **对产品反而是好消息，且要写进 MVP**：这个「已算 T、未核定 U」状态正是**任何新建项目的第一步天然状态**。产品把它做成显式的 `待核定` 状态（UI 显示"待核定 T=15 米" + 批量核定按钮），既是导入时的正常态，也是新建时的工作流起点 —— **一个状态两处复用**。真正要清洗的是 r332/r333 那两行 `T = "待定"`（文本塞进数值列）。

> 种群 2 的 4477 行里：N 非零 = **0**、O 非零 = **0**、P 有值 = **0** —— 整条公式链被完全绕开。**三条产品后果**：

1. **"自动算线长"不能作为卖点，必须改成"线长建议 + 置信度门控 + 强制人工确认"。** 系统对存量的真实能力是经验表：`(空间关系类, 线缆类型, 物理路径距离) → 长度`，**留一交叉验证（LOO，拿走该行自身数据后预测，代表"遇到没见过的新行"的真实表现）= 87.11%**；而原公式 `IFS(0.72P+Q)` 对全量 5104 行只有 **61.66%**。两个 87% 的巧合很好用：**87.6% 的行绕过公式 ↔ 经验表对它们 87.11% 可预测**，讲方案时可以互相印证。
2. **必须区分覆盖率，不能只说一个 87%**：A 类（同排面对面）LC-LC 很干净（`path=0→5m` 92.5%、`path=1~5→10m` 96~98%、`path=6~8→15m` 80~100%）；A 类 RJ45 `path=0` 是**唯一不纯的一格（`7m` 50.3% vs `5m` 38%，应标 LOW 强制人工）**；B 类（同通道跨侧）`O=1/2/3` 时**一律 15 米（98~100%），与线缆类型无关**；**C 类跨通道仅 37.5%~58.8%（260 行，5.1%）→ 强制人工**；**MPO A 84.4% / B 69.6% / C 37.5%（353 行，6.9%，走主干桥架而非排端走线架）→ 强制人工**。错误最集中的设备对：`存储核心交换机→存储接入交换机 1` MPO **错 86/128 = 67%**、`业务核心交换机→业务接入交换机 2` MPO **错 12/16 = 75%**、`管理核心交换机→带内交换机1` LC-LC **错 17/36 = 47%**。
3. **`IMPORTED` 模式是 MVP 硬需求，不能推到 v0.2。** 若不保留原值、不用策略门控，用户导入 V13 后会看到 **4477 行全部告警"长度与计算值不符"**——一个 88% 都是红字的产品，第一天就被判定不可用。故 `LengthPolicy` 必须是**四策略**（`GEOMETRIC | EMPIRICAL | MANUAL | IMPORTED`），`IMPORTED` 行**不参与不符告警**。

> **对外可量化收益（替代"自动算线长"的说法）**：**人工需逐行判断的 5104 行里，约 87% 由系统给出可信建议，只剩约 13%（C 类 + MPO + 少数高频错设备对）必须人工定。** 比"全自动"诚实，也比"全人工"有说服力。依据：ARCH §4.1A、RPT §5A（`.scratch/final_len.py`、`.scratch/gen_emp2.py`）。

### 5.4 v1.0 能复制（含 3D 的 gate）

| 项 | 内容 |
|---|---|
| **目标** | 换一个机房、换一个客户，**不改代码**就能用 |

| **验收标准** | 用第二个机房的真实数据，**零代码改动**导入并出表；3D（若做）达 200 柜 + 3000 设备 ≥ 30 fps（AC-7） |
| **工作量** | 30~40 人日（不含 3D）；3D 另加 **30~40 人日** [假设] |
| **风险** | ①通用化最容易变成"配置文件地狱"（缓解：先做 2 个真实机房，第 3 个再抽象）；②3D 一旦开工就停不下来（缓解：见下 gate） |

**3D 的三个 gate（全部通过才开工，任一不过就继续往后放）**：**G-3D-1 有客户愿意单独付钱**（至少 1 个客户把 3D 列为单独付费项，≥ 合同额 15%）；**G-3D-2 汇报场景被验证 ≥2 次**（2 次真实"给领导/甲方汇报"，现有 2D + PDF 明确不够用）；**G-3D-3 2D 与表格已稳定**（v0.3 已交付且连续 2 个月无 P0 缺陷）。
> 这三条不是保守：3D 是**唯一一个"投入 30~40 人日、收益无法量化"的模块**。R04 §5.3 判断"投入产出比最低"，我们同意，但保留一个可验证的开闸条件而非永久否决。

### 7.2 五条护城河（H1~H3 沿用 R04；H4 为审计能力、H5 为端口分配引擎，均为本文新增）

> **编号说明**：R04 §5.2 只给了 H1/H2/H3。本文在调研后追加两条，其中**H4（数据/几何审计）**是产品立场层面的壁垒，**H5（确定性端口分配引擎）**是反解第三条新结论后追加的技术壁垒。两者独立成立，缺一不可。

| # | 护城河 | 为什么难被抄 | 技术壁垒 | 可持续性 | 最可能被谁攻破 |
|---|---|---|---|---|---|
| **H1** | **双向保真**（导出 Excel → 现场改 → 导回，不丢列/公式/合并单元格，且能 diff） | 需要自己实现 Excel 的样式与公式模型，还要容错客户"乱改"。这是脏活，开源项目和商用 DCIM 都不愿意碰（它们要你"在系统里改"） | 列序+表头文本+列宽+冻结+数据验证+公式表达式+合并单元格六件套；幂等导入需"三段式稳定业务键 + MOVED 软匹配"（R03 §9A） | **高**。抄的人要先赔 3~6 个月工期，且客户不会因为"支持导出"就换供应商 | AI 生成代码降低了实现门槛，但**容错规则是从 5113 行真实脏数据里长出来的**，抄不走 |
| **H2** | **真实几何 → 真实线长** | 线长不是查表，取决于机柜在房间里的位置、通道走向、跨几个柜、是否同通道，需要"平面图→通道→机柜→U位"完整坐标链 | A 类同排 `O = 列差绝对值` 93.1%、B 类排端公式 98.0%、N 公式 98.6%；**C_MAX[403]=38 / C_MAX[404]=18 必须建模为一等公民** | **中高**。公式本身可被反推（我们自己就是反推出来的），但**"每排端部才有走线架"这个物理洞察 + 52 处错误样本**是数据资产 | 任何拿到同一份 xlsx 的人，3 个月也能反推出 90%。**所以 H2 不是永久壁垒，是 12~18 个月的时间窗** |
| **H3** | **异构设备型号库** | 客户设备混编：鲲鹏 920（ARM）与海光 7390H（C86）并存，交换机分业务/存储/管理/带内/带外五张网 + 独立密评设备区，22 类设备 28 种型号 | 端口模板「板卡×槽位×端口数」；端口命名双轨（`100GE1/0/1` / `千兆1` / `IPMI`）；MPO 1:N breakout | **高**。这是逐项目积累的资产，AutoLink 131 款 GPU 精选库覆盖不了政务云杂牌军 | 只能靠时间积累。**反向风险**：如果客户设备同质化（比如都买华为全家桶），这条护城河会消失 |
| **H4** | **数据 / 几何审计能力**（本文新增，**这是别人完全没有的卖点**） | 别人把"算得准"当目标，我们把"**能证明你算错了**"当目标。这需要三个前提同时具备：有真实的几何基准、有可复现的确定性公式、有足够大的错误样本做验证 | 52 处 N/O 偏差逐条复核 **100% 为源数据错误**（N 错则 O 必错，N错&O对=0 例）；13 对 U 位物理重叠；**12 处型号归属冲突**；**10 处实例重名**；1 组名称变体；5111 条跨表不一致；**126 行"模块有值但无批次"** | **最高**。这是"能力 + 立场"的组合：商用 DCIM 不敢说客户数据错（它要卖系统），开源工具没几何基准算不了，Excel 自己不会查自己 | 难以被攻破，因为它要求**同时**具备 H2 的几何基准与"敢于指出客户错误"的产品立场 |
| **H5** | **确定性端口分配引擎**（本文新增，依据 ARCH03） | 交换机哪个口接服务器哪个口，看起来是"现场随便插"，实测是 **100% 确定的规则**：`port = base + 组内位次`（3850/3850 = 100.00%）、`slot ≡ (i+φ) mod 8`（112/112 组 = 100%）、服务器口→交换机型号 64 条映射零歧义 | **三条规则必须从真实项目数据里反解**：没有 3850 条真实端口记录 + 112 组组结构，抄不到；靠猜或靠"通用做法"只能得到 60~70% | **最高，且门槛高于 H2**。H2/线长公式可以用几何常识推（隔几个柜就是几个长度），**端口相位无法用常识推**——它是这家设计院的内部约定 | 只有拿到同类真实项目数据的人能反解。**AI 自动生成代码无法缩短这个数据门槛** |

### 7.4 H4/H5 的商业价值（为什么它们是护城河而不是附属功能）

| 场景 | 没有 H4/H5 | 有 H4/H5 |
|---|---|---|
| 第一次接触 | "我要你重建一遍我的表"（防御） | "我 5 分钟告诉你表里哪 52 行算错了、哪 3771 行缺几何量"（好奇） |
| 报价谈判 | 比功能、比价格 | 比"你上次那 829 根线多买了 244 根" |
| 存量项目切入 | 要么全量迁移（重），要么不进入 | 体检报告即可交付价值，**不需要迁移** |
| 竞品对比 | 功能表对齐，容易被 AutoLink 比下去 | 竞品无法回应**四个 demo**："你有 3771 行缺几何、你公式有 bug 多买了 49 行、你 4 台交换机撞车、你 126 行模块不知属于哪期"——**这四句它一句都答不上** |
| 生成能力对比 | 只能比"谁生成得快"（我们必输） | "它生成一张**新**表，我们把**你这张**表生成出来，还包括你原来填错的 52 处" |

> **所以产品顺序必须是：先体检（M7）→ 再算（M4）→ 再生成（M0/M3）→ 再出表（M5）→ 最后才是编辑能力。** 这也是 §6.6 把 13 条 FR-D 全部前移到 v0.1 的理由。

### 7.5 护城河的诚实评估：哪条最弱

| 护城河 | 评分（1-5） | 说明 |
|---|---|---|
| H1 双向保真 | 4 | 脏活壁垒真实存在，但**不是不可逾越**；若客户改用"系统为准"，价值下降 |
| H2 真实几何 | **3（最弱）** | 公式可反推、代码可重写，**时间窗只有 12~18 个月** |
| H3 型号库 | 4 | 靠项目积累，但**依赖客户设备多样性** |
| H4 数据/几何审计 | **5** | 能力+立场的组合，最难被复制 |
| H5 端口分配引擎 | 4（规则若通用则 5） | **技术门槛最高**，但**通用性未验证**（§10 R3）：换机房/换厂商若失效，就退化成"一个项目的定制逻辑" |

> **战略含义**：不要靠 H2 卖产品（会被抄），要**用 H4 打开门、用 H5 拉开差距、用 H1 留住人、用 H3 提高替换成本**。**H2 是入场券，不是护城河。**

### 8.3 为什么不走 SaaS / 年订阅（5 个硬理由）

| # | 理由 | 依据 |
|---|---|---|
| 1 | **客户内网物理隔离**，SaaS 直接出局 | 政务云/国资云要求内网隔离 + 等保（R04 §7.1） |
| 2 | **项目制预算**：项目结束预算归零，年订阅第二年会掉 | R04 §4.1 结论 3 |
| 3 | **采购流程**：一次性资产入账 vs 年年走服务采购，后者流程更重 | 客户是国资体系 |
| 4 | **数据主权**：布线表含机房布局、设备型号、IP 段，属敏感信息，客户不接受出内网 | 密评设备区、政务外网区的存在 |
| 5 | **销售成本**：SaaS 需要持续获客，我们的获客靠"项目交付口碑"，是一次性动作 | 团队规模决定 |

> **唯一的例外**：B 档的"年"其实是**订阅式买断**（不续费仍可读），不是 SaaS。这个措辞在合同里要写清楚。

### 8.4 单位经济模型（**全部为假设，用于判断商业可行性，不用于对外报价**）

| 项 | 假设值 | 推算 |
|---|---|---|
| 全周期开发量 | 108~140 人日 | §5.2 |
| 人日综合成本 | ¥1,500/人日 [假设] | 含社保/管理摊销 |
| 开发成本 | **16~21 万元** | 108×1500 ~ 140×1500 |
| A 档毛利 / 回本点 | ¥29,800 − 交付成本（部署+导入+培训约 5 人日 ≈ 7,500 元）→ 毛利 ≈ **2.2 万元/单**；16~21 万 ÷ 2.2 万 ≈ **8~10 单**回本 | 需要 8~10 个同类项目 |
| B 档年毛利 | ¥88,000 − 年维护人力（约 20 人日 ≈ 3 万）≈ **5.8 万元/客户/年** | 3~4 个 B 档客户即可覆盖年维护团队 |
| C 档毛利 | ¥198,000 − 开发成本（16~21 万）≈ **接近 0** | **C 档不是用来赚钱的，是用来打标杆、换口碑与案例授权的** |

> **结论**：这是一个**小市场、高单价、低复购**的生意。商业上成立的前提是：①单个 A 档交付成本压到 ≤5 人日；②在 12~18 个月的时间窗内拿到 ≥8 个同类项目（H2 护城河窗口期）。
> **如果拿不到 8 个项目**，则应该把产品转为 C 档"源码交付 + 定制"模式，做项目制外包，不做产品。

| 陷阱 | 表现 | 应对 |

| **按机柜/按端口计价** | 客户拿 dcTrack 的 $234/柜 来比，觉得我们贵 | 坚决不按机柜算；**按项目买断**，把"无限机柜"当卖点 |

> **四条最关键的 R1 / R3 / R3b / R7 是同一件事的四个面**：**我们反解出来的所有规则，都可能是"这一个项目的内部约定"，而不是物理规律。** 它们共同指向一条设计原则——**从 v0.1 第一天，就把每一条反解规则做成"可配置 + 可校验 + 失败可降级"的三件套**：配置外置（改规则不改代码）、校验器兜底（不合格就报警）、降级通道（人工可接管，绝不假装算得出）。这条原则比任何单条风险缓解都重要。

### 12.3 一个必须顺带纠正的数据（不是问题，是事实修正）

> REQ §3.1 写"**289 条 U 被人为上调**"，与 RPT §5.1 的 T→U 转移矩阵不一致。按矩阵逐格核算（铅版实测，636 行全覆盖）：**一致 352、上调 103、下调 172、U 未填 9**（`352+103+172+9 = 636` 精确闭合）。**结论**：那个"289"是**"被调整过的行数"（一致之外的行 = 103+172+9 = 284，与 289 同量级但不是同一个量）**，不是"上调数"——**上调 103、下调 172，下调反而多 69 条**。
> **产品含义很重要**：既然工程师既会调高也会调低，`U` 编辑**必须双向开放**，不能设计成"只能加余量"（R03 R3）。本文 §4.3 M4、§10 R5 均按双向设计。
