## 2. 分工与概念界定：谁是「本端」谁是「对端」

反解前必须先纠正一个容易踩的坑：**`布线表` 的 `本端/对端` 取决于导出时的视角，不是固定的设备类别**。

实测 5113 行中，同一物理连线在两个方向上都有出现的情况 **为零**（即表是单向单份记录，无反向冗余）。因此所有分组统计都必须做 `for S,T in ((A,B),(B,A))` 的双向归一化，否则会把同一组切碎成两半。

本报告统一约定：

- **交换机侧**（Switched side）：`业务接入交换机 1`、`存储接入交换机 1`、`带内交换机1`、`带外交换机1` 等，端口名为 **CLI 板卡式** `100GE1/0/1`、`25GE1/0/25`、`GE1/0/21`。
- **服务器侧**（Server side）：`计算节点A（ARM）`、`计算节点B（C86）`、`EHDD云硬盘服务器1` 等，端口名为 **标签式** `万兆1`、`千兆2`、`25G1`、`IPMI`。
- **组**（Group）：`(交换机型号, 交换机实例名, 对端服务器型号)` 三元组。一组 = 一台交换机为某一类服务器提供的一条下联链路集合。
- **slot**：计算节点在机柜内的 2U 槽位序号，`slot_of(u) = (u_start − 3) // 4`。取值 0..7 对应 U 位 `3-4U / 7-8U / 11-12U / 15-16U / 19-20U / 23-24U / 27-28U / 31-32U`。

## 4. C2 — 交换机侧端口号 = 组内位次 + 起点（100%）

### 4.1 结论

对每个「组」，把组内节点按 `(机柜号 asc, U 位 asc)` 排序，第 `i` 个节点（0-based）使用的交换机端口号为：

```
port_number(node_i) = base + i
```

其中 `base` 是该组的端口起始号（组内最小端口号）。

**验证：3850 / 3850 = 100.00%，零例外。** 脚本 `.scratch/final_rule.py`、`.scratch/final_verify.py`。

### 4.2 `base` 的实际取值分布

| 组内最小端口号 | 组数 | 含义 |
|---|---|---|
| 1 | 91 | 一台交换机独占一个服务区间 |
| 9 | 7 | 一台交换机拆成两个服务区间，第 2 段从 9 起 |
| 17 | 7 | 第 2 段从 17 起 |
| 20 | 7 | 第 2 段从 20 起 |

> **一台交换机可以被拆成多个「接线块」**，分别服务不同区间的节点。这与 C8「一台 ToR 服务多少节点是设计变量」是同一现象的两种表现。产品模型里必须有「交换机 ↔ 节点区间」的多对多关系，不能假设一对一。

### 4.3 一个完整组的实例（`计算接入交换机(业务)-3` 的 44 个下联口）

```
port  1 -> ch2 rack 6  19-20U      port 12 -> ch2 rack 8  31-32U
port  2 -> ch2 rack 6  23-24U      port 13 -> ch2 rack 8   3-4U
port  3 -> ch2 rack 6  27-28U      ...
port  4 -> ch2 rack 6  31-32U      port 19 -> ch2 rack 8  27-28U
port  5 -> ch2 rack 7   3-4U       port 20 -> ch2 rack 9  31-32U
port  6 -> ch2 rack 7   7-8U       port 21 -> ch2 rack 9   3-4U
...
port 11 -> ch2 rack 7  27-28U      port 44 -> ch2 rack 11 31-32U
```

注意这里的**非直觉处**：`rack 6` 从 `19-20U` 开始（不是 `3-4U`），而 `rack 7/8/9/10` 从 `3-4U` 开始，`rack 8` 的第 8 个槽却是 `31-32U`。这**不是**数据错误，正是 C3 的相位规则。

## 5. C3 — U 位槽位相位 `slot_i = (i + φ) mod 8`（112/112 = 100%）

### 5.1 结论

```
slot_of(u_start) = (u_start − 3) // 4          # 取值 0..7
对组内第 i 个节点（按端口号升序）：
    slot_i ≡ (i + φ) mod 8                     # φ ∈ {0, 3, 4}
且 φ 在组内唯一（不随 i 变化）
```

**验证：112 组全部 φ 唯一，零例外。** 脚本 `.scratch/phase.py`。

### 5.2 φ 不是独立参数：φ = 组内首个节点的 slot

| 首节点 slot | φ | 组数 |
|---|---|---|
| 0 | 0 | 70 |
| 3 | 3 | 7 |
| 4 | 4 | 35 |

三者恒等，说明 **φ 完全由「组的起点从机柜第几个槽开始」决定**。这一条把参数从 2 个（base + φ）降到 1 个（base），因为 φ 可由首节点位置算出。

### 5.3 为什么会有相位偏移（物理含义）

一台交换机的下联节点区间可能在任意槽位开始：

- φ=0 → 从 `3-4U` 起，正常从上往下
- φ=4 → 从 `19-20U` 起，此时前半柜（`3-4U`..`15-16U`）已被**上一台交换机的节点**占用
- φ=3 → 从 `15-16U` 起，用于补齐尾段

因此 **相邻两台交换机的节点区间在机柜内首尾相接、不重叠**。这解释了为什么单看一个机柜，U 位不是从 `3-4U` 单调排到 `31-32U`——它是被多台交换机的服务区间"切开"的。

> **产品价值**：这意味着「U 位看起来乱」不是脏数据，而是拓扑约束的结果。任何"按 U 位排序就能推出端口序"的朴素实现都必然失败（实测 65.82%，见 §7）。

### 5.4 相位校验器（可直接落地的防错规则）

系统生成端口分配后，必须逐组校验：

```python
def validate_group(nodes_sorted_by_port):
    phis = {(slot_of(n.u_start) - i) % 8 for i, n in enumerate(nodes_sorted_by_port)}
    if len(phis) != 1:
        raise PhaseViolation(
            f"组内 U 位相位不唯一：{sorted(phis)}。"
            f"可能原因：①节点列表不连续（漏了某个槽位）②两个组的节点被混在一起 ③U 位填写错误"
        )
```

这条规则**不需要任何额外数据**，只靠 `(rack, u_start, port_number)` 三列就能检出人工排错。是零成本、高价值的校验项。

## 6. C4/C5 — 组内排序规则与命名规范

### 6.1 排序规则：`rack asc, U asc`

112 组内节点机柜号**严格单调不减（100%）**。结合 C3 的相位规则，组内节点的完整排序键是：

```
sort_key = (rack_seq, u_start)
```

⚠️ 注意 `rack_seq` 用的是**机柜编号**还是**平面图列坐标**要区分清楚：在通道两侧机柜编号是镜像的（见 [`01-线长算法反解报告.md`](01-线长算法反解报告.md) §3.2 柜号镜像陷阱）。本段的 112 组全部落在 403 房间且编号顺序与列坐标同向，因此两者等价；但在 404 房间或其他布局下不一定成立，**实现时必须用统一的 `rack_seq` 定义并单测**。

### 6.2 交换机实例名编码了物理位置

`业务接入交换机 1` 有 18 台实例服务计算节点A（630 条连线），实例名与位置严格对应：

| 通道 | 实例名 | 机柜 |
|---|---|---|
| ch2 | `计算接入交换机(业务)-1..6` | rack 2, 4, 7, 9, 12, 14（均 40U） |
| ch8 | `计算接入交换机(业务)-11..16` | rack 2, 4, 7, 9, 12, 14 |
| ch9 | `计算接入交换机(业务)-21..26` | rack 2, 4, 7, 9, 12, 14 |

规律：**十位数字 = 通道组（1→ch2, 2→ch8, 3→ch9），个位 = 机柜序**。

同族实例：
- `计算接入交换机(存储)-N` 在 ch2/8/9 的 rack 3, 5, 8, 10, 13, 15（与业务接入**错开一个柜**）
- `计算带内交换机-N`、`计算带外交换机-N` 遵循同样的编码

> **产品落地**：可做「命名规范校验」——用户输入 `计算接入交换机(业务)-23` 但把它放在 ch2 时告警。同时这个编码给出了**冗余域/故障域边界**：`-21..26` 这 6 台自成一个服务组，服务于 ch9 的一段连续节点区间。

## 7. C6 — 交换机上联口：位置固定、用途固定

实测交换机侧非下联端口（对端不是计算节点）的分布：

| 交换机端口 | 对端设备 | 出现次数 | 推断用途 |
|---|---|---|---|
| `100GE1/0/1` ~ `100GE1/0/4` | `业务核心交换机` | 各 30 | **上联核心**（每台业务接入交换机 4×100G 上行） |
| `100GE1/0/5` ~ `100GE1/0/6` | `业务接入交换机 1` | 各 26 | **横向互联**（stack / M-LAG） |
| `100GE1/0/7` ~ `100GE1/0/8` | `业务接入交换机 1` 或 `2` | 各 4 | 横向互联（跨型号） |
| `10GE1/0/48` | `业务接入交换机 1` | 26 | **堆叠/管理口**（注意是 48 号，跳号非连续） |
| `25GE1/0/1` ~ `25GE1/0/19` | `带内交换机1` / `带外交换机1` / `网络功能服务器` | 各 2 | 带内/带外接入 |

结论：**端口不是平等的一张表，而是有角色的。**

### 7.1 必须建模 `port_role` 枚举

```python
class PortRole(StrEnum):
    DOWNLINK  = "downlink"    # 下联服务器（业务核心交换机 → 计算接入）
    UPLINK    = "uplink"      # 上联核心（接入 → 核心）
    PEER_LINK = "peer_link"   # 横向互联（接入 ↔ 接入，stack/M-LAG）
    STACK     = "stack"       # 堆叠/带外管理
    MGMT      = "mgmt"        # 管理口（政务外网表的 `GL`）
    SPARE     = "spare"       # 空闲
```

这个枚举决定三件事：
1. **端口分配算法的候选池**（下联只能挑 `downlink` 口，不能占用上联口）
2. **校验规则**（上联口数量必须与冗余策略匹配，如 4 上联 = 2 主 2 备）
3. **可视化渲染**（2D U 位图上不同角色用不同颜色，是施工人员最需要的图）

### 7.2 `业务核心交换机` 的端口名有 85 种，末位跳号

实测 `业务核心交换机` 端口名为 `100GE1/0/1`..`100GE1/0/36`、`100GE2/0/1`..`100GE2/0/36`、`100GE3/0/33`..`100GE3/0/36`、`25GE1/0/1`..`25GE1/0/8`、`25GE1/0/48`。

**注意 `25GE1/0/48` 是孤立存在的，不连续。** 这印证了端口面板模板不能靠"1..N 连续生成"来猜，必须显式建模（见 [`00-源数据实测基线.md`](00-源数据实测基线.md) §5）。

|---|---|---|---|
| `(本端型号, 本端端口名) → 本端模块` | 257 | **0** | 100% |
| `(对端型号, 对端端口名) → 对端模块` | 110 | 5 | — |
| 合并（排除歧义键） | **328 权威键** | 5 | **97.54%**（1112 正确 / 28 错误） |

**5 个歧义键的原因已定位，全部是源数据人工填错或场景差异：**

| 歧义键 | 值分布 | 原因 |
|---|---|---|
| `网络功能服务器` + `25G1/25G2/25G3/25G4` | `设备自带`×4 / `25G-SR`×2 | 同一台服务器在不同批次被填了不同值 |
| `分线接入交换机` + `25GE1/0/48` | `25G-SR`×2 / `100G-SR4`×2 | 该端口是 100G 口（见 §7.2 跳号问题），填 `25G-SR` 是错的 |

### 8.3 规则法 vs 查找表法

尝试过的**纯规则推导**（不看历史数据，只按 `线缆类型 + 端口速率 + 是否服务器`）：

| 规则 | 命中率 | 结论 |
|---|---|---|
| 按本端端口速率的 nominal speed 映射 | 97.28% | 可用，但有系统性偏差 |
| `服务器侧一律=设备自带` + `RJ45 且任一端≥10G=光转电` | 96.23% | 更差 |
| 按 `min(两端速率)` 映射 | 差（未通过） | 错，因为服务器侧不看速率 |
| 端口类型感知（光口+铜缆=光转电） | 97.28% | 与第一条等价 |

**纯规则的系统性偏差清单（说明规则法不能单用）：**
- `管理核心交换机` 的 `25GE1/0/x` 口实际插 `10G-SR`（25G 口降速跑 10G）——规则算不出，只能查表
- `分线接入交换机` 的 `25GE1/0/48` 实际是 `100G-SR4`（端口名骗人）——规则算不出
- `网络功能服务器` 的 25G 口有的自带、有的需配 `25G-SR`——规则算不出

> **结论：模块列必须「查找表优先 + 规则兜底 + 人工可改」三段式。** 查找表来自历史项目（本项目的 328 条）；规则用于查找表未覆盖的新型号；人工可覆盖并回写查找表。这是「经验沉淀」的又一个实例，与线长 U 值同理。

### 8.4 覆盖率的诚实陈述（重要，不要夸大）

**查找表法只能覆盖 37.61% 的行（1923/5113 两端都可推导）**，因为源数据的模块列本身只填了 11.1%。这不是算法能力问题，是**缺训练数据**。

产品应对策略：
1. **模块列默认留空**，不强行生成（生成错比空更糟——采购会多买）。
2. 提供「模块批量填充」功能：用户选一批行 → 系统给查找表建议值 → 用户确认 → 回写。
3. **模块需求汇总表**只在有值的行上汇总，并在报表上显式标注「覆盖 570/5113 行，其余待补」，绝不能静默按 37.61% 推算全量采购量（那会**少买**模块，是安全事故）。

### 8.5 「首期」标记与模块列的错位（数据体检的新发现）

交叉表 `(备注有值, 模块有值)`：

| 备注=`首期` | 模块有值 | 行数 |
|---|---|---|
| ✘ | ✘ | 4541 |
| ✘ | ✔ | **126** |
| ✔ | ✘ | **2**（行 337、341） |
| ✔ | ✔ | 444 |

126 行「模块有值但没标首期」集中在：`带内交换机1→计算节点A` 40、`带内交换机1→带内交换机1` 24、`带内交换机1→SSD云硬盘服务器` 24、`带外交换机1→计算节点A` 20、`存储接入交换机 1→SSD云硬盘服务器` 12。

**这是必须做成校验规则的缺陷**：模块（要采购的）与首期标记（哪期采购的）不一致 → 采购范围界定不清。系统应报「模块已填但未标记批次」告警。

## 9. 已证伪的模型（不要重复尝试）

| 假设 | 实测命中 | 失败原因 |
|---|---|---|
| 端口号 = 节点在「全局序（chat,rack,U）」中的位次 − 区间起点 + 1 | 2534/3850 = **65.82%** | U 位不单调：组的起点可能是 `19-20U` 或 `15-16U`，全局序与端口序不同构 |
| 端口号 = 全局序 + 「柜内起点 = 最大 U」旋转修正 | **0.00%** | 旋转假设彻底错，相位不是简单旋转 |
| 端口号 = 柜内位置索引差 | — | 判据错误：端口序的基准在交换机侧，不在柜内 |
| 组内节点按 U 位单调升序 | 70/112 = 62.5% | 相位偏移导致 42 组"看起来不升序"，实为合法 |
| φ 是独立人工参数 | — | φ ≡ 首节点 slot（100%），是派生量 |

> **教训（写进架构约束）**：任何"按物理位置排序就能推出端口号"的实现都是错的。正确模型是 `端口号 → 节点位置`（正向生成），而不是 `节点位置 → 端口号`（反向猜测）。

## 10. 产品与架构指令

### 10.1 「接线意图」三层模型（产品核心概念）

```
第一层：设备-网络角色映射   （型号 + 端口名 → 交换机型号）   64 条，可固化为模板
第二层：节点排序规则        （rack asc, u_start asc）        一条规则
第三层：端口分配规则        （port = base + i，slot ≡ i+φ mod 8）两条规则
```

用户只声明第一层的角色归属 + 第三层的 base（或让系统自动排），中间全部自动推导。**这是把 5113 行人工表变成约 30 行配置的关键。**

### 10.2 给架构文档的 6 条硬要求

1. **`port_role` 必须是一等枚举**，且进入端口分配算法的候选池过滤条件。
2. **`switch_group` / `pod` 必须建模**：一台 ToR ↔ 节点区间是多对多，不是一对一。`base` 是「交换机-节点区间」关系上的属性，不是交换机上的属性。
3. **`phi` 不落库**，由 `slot_of(首节点 U 位)` 实时算出；落库会导致数据不一致。
4. **相位校验器必须实现**（§5.4），作为「端口自动分配」功能的守门员。
5. **端口面板模板必须允许"标称端口数 ≥ 实际使用端口数"**（见基线 §5），因为 `业务核心交换机` 有 `25GE1/0/48` 这类孤立端口。
6. **命名规范校验作为 P1**：从实例名解析通道组/柜序，与实际位置比对。

### 10.3 自动化覆盖率重估（重要）

原以为「自动化生成布线表」很难。现在看：

| 布线表组成部分 | 是否可自动 | 依据 |
|---|---|---|
| 本端/对端设备型号与实例 | 🟢 100% | C1 映射 + 用户声明角色 |
| 本端/对端通道、机柜 | 🟢 100% | 用户声明 + 设备台账 |
| 本端/对端 U 位 | 🟢 100% | 设备台账（`UNIQUE(rack_id, u_start)`） |
| 本端/对端端口名 | 🟢 100% | **本文 C2/C3** |
| 线缆类型 | 🟢 100% | 设备对 → 线缆类型矩阵（基线 §11） |
| 跨机柜 N | 🟢 98.6% | 01 号文档 §3.1 |
| 间隔机柜 O | 🟢 91.8%（A 93.1% / B 98.0% / C 60.0%） | 01 号文档 §3.2 |
| 机柜数量 P / 柜间 R / 线缆2 S / 长度1 T | 🟢 100% | 公式链，01 号文档 §2 |
| 线缆长度 U（核定值） | 🔴 不可算法复现 | 01 号文档 §4，必须人工核定 + 留痕 |
| 本端/对端模块 | 🟡 查找表 97.54% 准，但只覆盖 37.61% 的行 | §8，源数据只填了 11.1%，缺训练数据 |
| 备注 | 🟡 人工 | 可选 |

**结论：25 列中 22 列可全自动，1 列（本端/对端模块）半自动可给建议，1 列（核定长度 U）必须人工但可给建议值，1 列（备注）自由文本。** 这块比原先估计的乐观得多，应作为产品第一卖点写进规划。
