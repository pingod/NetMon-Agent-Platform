## 1. 领域建模

### 1.1 从交付物反推的实体清单

依据 V13 全 9 个 sheet + 3 份外部样例，实体关系如下（`[实测]`）：

```
机房 Site (404机房 / 403机房，各标称 4kW/总181架)
 └─ 房间 Room (404 / 403)
     └─ 通道 Aisle (1..14，本项目用 1/2/3/8/9)
         └─ 排 Row (每通道 2 排，面对面)          ← 关键：排是"跨机柜"计算的原子单位
             └─ 机柜 Rack (编号在该排内 1..13 / 14..27)
                 ├─ 列头柜 (整柜 42U，C列)
                 ├─ 空调 (整柜 42U 占位，与机柜同高)
                 ├─ 柱 (整柜 42U 占位)
                 └─ U位槽位 Slot (42 个 U；业务上用 2U 对齐)
                     └─ 设备 Device (跨 1..10 U)
                         └─ 端口 Port (物理口 + 别名)
                             └─ 连线 Link (= 布线表 1 行)
                                 ├─ 线缆计算块 (P/R/S/T)
                                 └─ 核定长度 U
```

### 1.2 机柜编号与几何规则（`[实测]`）

**这是全系统最关键的空间基准，必须精确落库。** 实测 129 个机柜位分布：

| 通道 | 所在房间 | 排数 | 机柜数 | 编号范围 |
|---|---|---|---|---|
| 1 | 404 | 2 | 27 | 排1: 1..13，排2: 14..27 |
| 2 | 404 | 2 | 25 | 排1: 1..12，排2: 13..25 |
| 3 | 404 | 2 | 25 | 排1: 1..13，排2: 14..25 |
| 8 | 404 | 2 | 27 | 排1: 1..13，排2: 14..27 |
| 9 | 404 | 2 | 25 | 排1: 1..12，排2: 13..25 |

**通道↔排的物理映射（`[实测]` 几何，从「机房平面图」+ U 位点位图双向确认）**：
- 404 机房含通道 1/2/3（东侧）与 8/9（西侧）；403 机房含通道 4/5/6/7
- 每个通道 = 两排机柜面对面（冷通道封闭），排间是走道
- 排内机柜沿 Excel 列方向排列，**每 1 个机柜占 5 个 Excel 列**（列宽 5）→ `Excel 列距 / 5 = 机柜序号差`
- **编号走向不对称**：同一排内，前半段机柜号沿列递增方向**递减**，后半段**递增**。实测 rowIdx0：`c8=r13 c13=r12 … c82=r1`；rowIdx1：`c8=r14 c13=r15 … c82=r27`。这个"折返"是真实物理布局（面对面两排共用一个编号序列），**不能用单一线性公式跨排换算**

**空调/柱占位（`[实测]`）**：空调与柱是**整列 42 行合并单元格**，与机柜同高，占据机柜编号序列中的位置但不占设备：
- 通道 1 排1：空调在 c28/c47/c67（3 处）；排2：c28/c67（2 处）
- 通道 2 排1：c28/c67 + 柱 c43/c47（`AQ104:AQ145`/`AU104:AU145` = '柱'）；排2：c28/c67
- 通道 8/9：空调在 c23/c43/c62 等**不同列位**（与通道 1-3 不同）
- 结论：**每个通道的缺位（空调/柱）位置不同，不能硬编码，必须作为参数表落库**

### 1.3 U 位与设备占位表示法（`[实测]`）

**U 位梯绘制规则**：每个 48 行块 = 一排机柜；块起始行 `lr`，标签占 `lr..lr+1`（合并），U 位梯从 `lr+2` 开始：
```python
U = 42 - (row - (lr + 2))     # lr+2 → 42U，lr+43 → 1U
```
**机柜高度 = 42U**（实测 U 值 42→1，非标准的 47U）。

**设备占位表示法 = 跨行合并单元格**，设备名写在合并区首格：
- `BT34:BT43`（10 行）= 存储核心交换机-1，占 **U34-U43，10U 高**
- `AZ26:AZ27`（2 行）= 网络功能服务器-7，占 **U26-U27，2U 高**
- 布线表侧对应写法：`3-12U`（10U 高核心交换机）、`3-4U`（2U 服务器）、`40U`（1U 交换机）
- 全表 13 种 U 位字符串（`[实测]`）：`11-12U,15-16U,19-20U,23-24U,27-28U,3-12U,3-4U,31-32U,34U,37U,38U,40U,7-8U`

**设备 U 高（`[实测]`，含频次）**：
| U 位表示 | 高度 | 设备角色 | 行数 |
|---|---|---|---|
| `3-12U` | 10U | 业务核心交换机 / 存储核心交换机 | 167 + 131 |
| `40U` | 1U | 存储接入交换机 1 / 业务接入 / 管理核心 | 1380 + 1190 + 79 |
| `37U` | 1U | 带内交换机1 / 业务接入 | 1380 + 11 |
| `34U` | 1U | 带外交换机 1（含尾随空格脏值）/ 带内 | 76+58+43 |
| `19-20U` | 2U | 广域网链路负载均衡 | 5 |
| `38U` | 1U | （极少） | 2 |

**业务槽位规律（`[实测]`，极重要）**：
- **服务器统一占 2U，8 个固定槽位**：起 U = `3,7,11,15,19,23,27,31`（每柜 8 台）
- **交换机占 1U，固定槽位**：`34U / 37U / 38U / 40U`（柜下部）
- **核心交换机占 10U，固定槽位**：`3-12U`（柜上部）
- 实测 ch2 r1..r12 每柜槽位：`[3,7,11,15,19,23,27,31]`（8 台服务器），部分柜另加 `37U/40U`（接入交换机），r8 出现 `38U`
- **U 位起分布（对端视角，全表）**：`{3:644, 7:622, 11:601, 15:601, 19:602, 23:563, 27:476, 31:476, 34:20, 37:169, 38:2, 40:351}`

### 1.4A 介质层建模：连接器 / 光模块 / 极性（`[标准]` + `[实测]` 交集）

> 本节的通用知识标 `[标准]`，凡有用户数据佐证的标 `[实测]`。用户表格里**没有** breakout、极性、单模/多模字段（`[实测]` 25 列中不存在），因此这部分是**产品的数据模型设计**，但必须与实测的 3 类线缆类型对齐，否则无法落地。

**A. 本项目实际用到的介质组合（`[实测]` 唯一 3 种枚举值）**

| 线缆类型 | 连接器 | 介质 | 模块 | 实测行数 | 对应速率 |
|---|---|---|---|---|---|
| `LC-LC` | LC 双工（2 芯） | 多模 OM4（推断，见下） | `10G-SR` / `25G-SR` / 设备自带 | 2685 | 10G / 25G |
| `RJ45` | RJ45 | 铜（Cat6/6A，推断） | `一` / `光转电` | 2089 | 1G |
| `MPO` | MPO-12（MTP 为 MPO 的高密度商用名，二者互通常用） | 多模 OM4（推断） | `100G-SR4` | 353 | 100G |

> `[待核实]` 用户表**未记录**单模/多模与光纤等级。但从模块型号反推：`10G-SR` / `25G-SR` / `100G-SR4` 中的 **`SR` = Short Reach，即多模短距**（`[标准]` IEEE 802.3：SR 用于 MMF，最远 100m@10G / 100m@25G / 100m@100G）。若现场出现 `LR`（Long Reach，单模 10km），说明走的是跨楼/长距场景 —— **本项目 636 行长度最大 40m，全部 < 100m，与 SR 多模的传输距离上限一致**，可交叉印证。

**B. 光模块 ↔ 线缆类型 ↔ 端口速率的三元一致性（`[实测]` 零例外规则）**

```python
MODULE_RULES = {
    # (rate_Gbps, media) -> (cable_type, allowed_modules)
    (1,   "copper"): ("RJ45",  {"一", "光转电"}),          # 实测 234 + 12
    (10,  "optical"): ("LC-LC", {"10G-SR", "设备自带"}),   # 实测 117 + 5
    (25,  "optical"): ("LC-LC", {"25G-SR"}),               # 实测 105
    (100, "optical"): ("MPO",   {"100G-SR4"}),             # 实测 90
}
```

`[实测]` 反例清单（必须能被产品识别并告警，共 19 行）：

| 现象 | 行数 | 性质 |
|---|---|---|
| `25GE` 端口配 `10G-SR` 模块 | 19 | **降速使用**：25G 交换机口插 10G 模块 → 线缆仍是 LC-LC，但速率跑 10G。合法但需标记 |
| `25G` 用 `光转电` 模块 | 12 | **25G 电口**（`[实测]` 备注 F34 逐字："6台密评设备，每台均配2个电口，上联交换机为25G8A，线缆使用RJ45的话，交换机侧需要配光转电模块"） |
| `100GE` 用 `LC-LC` | 2 | 模块 `100G-SR4` 但线缆类型填 LC-LC → **可能填错**（100G-SR4 是 MPO 模块） |
| `GE` 用 `LC-LC` | 1 | 1G 光口（1000BASE-SX）→ 合法但罕见 |

> **产品规则**：`cable_type` 由 `(端口速率, 端口介质)` 决定（§7.1）；`module` 由 `(端口速率, 线缆类型)` + 人工覆盖决定。**两者必须交叉校验**（规则 C8/C9/C24）。

**C. Breakout（拆分）建模 —— 本项目未使用，但架构必须预留**

`[实测]` 本项目 **无一条 breakout**：353 条 MPO 全部是整链路 100G↔100G，无 `1×400G → 4×100G` 或 `1×100G → 4×25G` 的拆分记录。

`[设计]` 但架构必须支持，因为这是 400G 时代的标准做法：

```
PhysicalPort(400G, MPO-16)
  └─ BreakoutCable(400G → 4×100G, MPO-16 → 4×MPO-12 或 4×LC)
       ├─ LogicalPort(100G, lane 0)
       ├─ LogicalPort(100G, lane 1)
       ├─ LogicalPort(100G, lane 2)
       └─ LogicalPort(100G, lane 3)
```

建模要点：
- `Port` 必须有 `parent_port_id` + `lane_index` + `capacity_divisor`
- **一条物理连线占 1 个 `Cable` 记录，但生成 N 条逻辑 `Link`** → 布线表里应输出 N 行（每逻辑链路一行），长度字段相同
- 线长计算不变（同一根物理线缆），但**模块数量按物理端口计**
- `[待核实]` 用户未来是否会上 400G？若上，`MPO-16` 与 `MPO-12` 的极性兼容性是必须确认的现场问题

**D. MPO 极性（polarity）—— 产品必须建模，用户数据无法反推**

`[标准]` TIA-568 定义三种 MPO 极性方案：

| 方案 | 结构 | 适用 |
|---|---|---|
| **Method A**（直通） | 两端 Key 上-下，光纤 1↔12 直连 | 需配合"跳线对"使用 |
| **Method B**（交叉） | 两端 Key 上-上，光纤 1↔12 交叉 | **最常用**，直连收发对齐 |
| **Method C**（对折） | 两端 Key 上-下，中间对折 | 少见 |

`[设计]` 产品规则：
- `Cable` 实体增加 `polarity` 字段，默认 `B`
- **校验**：一条 MPO 链路两端必须是"发送口→接收口"的配对（`Tx↔Rx`）；若两端都是 `Tx` 或都是 `Rx` → 报 **P 级错误**（光路不通）
- 用户数据里 `100G-SR4` 模块自身已内含 4 个 lane 的 Tx/Rx，MPO-12 的 12 芯中 8 芯用于 4×Tx + 4×Rx，4 芯空闲 → **极性错误的后果是整条链路不通，必须在设计阶段校验**

**E. AOC / DAC 直连铜缆 —— 本项目未使用**

`[实测]` 全项目无 `AOC` / `DAC` / `直连` 字样。本项目同机柜互联（111 行）全部用 `LC-LC` 光纤跳线或 `RJ45` 网线，**不用 DAC**。

`[设计]` 但架构应区分：

| 类型 | 说明 | 长度上限 `[标准]` | 本项目 |
|---|---|---|---|
| **DAC**（无源直连铜缆） | 交换机↔交换机短距 | 1–3m（10G）/ 1–5m（25G） | 未使用 |
| **AOC**（有源光缆） | 交换机↔交换机中距 | 1–30m | 未使用 |
| 光模块 + 跳线 | 本项目方案 | 见 SR 上限 100m | ✅ 全部 |

> **产品建议**：`cable_type` 枚举应扩展为 `{LC-LC, RJ45, MPO, DAC, AOC}`，但**默认只暴露本项目用到的 3 种**，避免用户误选。

**F. 与 TIA-942 / TIA-568 的关系（`[标准]`，说明为何不用标准的 90m 规则）**

| 标准规定 | 内容 | 本项目为何不直接套用 |
|---|---|---|
| TIA-568 水平布线 | 永久链路 90m + 两端跳线各 5m = **100m 信道** | 数据中心**机柜间**互联不是"水平布线"（那是楼层配线架→工作区），而是**设备间/主干**场景，走的是跳线而非永久链路 |
| TIA-942 数据中心 | 区分 MDA/HDA/ZDA/EDA 分层，主干光纤支持 300m（OM4 多模） | 本项目是**同一房间内**机柜互联（最大平面跨度 ~40m），远小于主干上限，**不做标准限值校验**，只做"是否超过所选模块的 SR 距离上限"校验 |
| TIA-568 跳线长度 | 设备跳线通常 2–5m | `[实测]` 用户 `Q`（机内线缆）= 5m（光纤）/ 7m（铜），**与标准一致** |

> **关键结论**：本项目线长的量级（5–40m）由**柜间经验公式**（0.72m/柜）决定，**不是**标准限值决定的。因此产品的校验重点是「**长度是否足以物理连通**」（不能短于几何最短路径），而非"是否超过标准上限"。**这是为什么本方案用自己的档位表而不是 TIA 的 90/100m 规则** —— 标准规则在这里不约束任何一条连线（全部远低于上限），套用只会产生噪声告警。

### 1.5 连接意图模型（`[实测]`，自动布线的输入）

**每台服务器接哪些交换机，由"网卡口名 → 网络平面 → 交换机角色"三级映射决定**。铁证（`计算节点A（ARM）-1` 全部 7 条连线）：

| 网卡口 | 连接的交换机角色 |
|---|---|
| `IPMI` | 计算带外交换机 |
| `万兆1` | 计算接入交换机(业务) |
| `万兆2` | 计算接入交换机(存储) |
| `万兆3` | 计算接入交换机(业务) |
| `万兆4` | 计算接入交换机(存储) |

## 3. 线长公式（核心资产，含反推证据与全表校验）

### 3.1 公式逐字提取（`[实测]`，openpyxl `data_only=False`）

```excel
P2 (机柜数量)   = N2+O2
R2 (柜间线缆)   = P2*0.6*120%
S2 (线缆2)      = R2+Q2
T2 (线缆长度1)  = _xlfn.IFS(
                    S2<=5,   5,
                    S2<=6,   7,
                    S2=7,    7,
                    S2<=8.5, 10,
                    S2<=13,  15,
                    S2<=17.5,20,
                    S2<=22,  25,
                    S2<=27,  30,
                    S2<=32,  35,
                    S2<=37,  40
                  )          ← 数组公式 (ArrayFormula)
U2 (线缆长度)   = 人工字面值（非公式）
Q2 (机内线缆)   = 人工字面值（非公式）
```

**参数解读**：
- `0.6` = 单机柜等效柜间距（米）
- `120%` = 20% 敷设余量
- 乘积 `0.6 × 1.2 = 0.72` m/柜 → **等效系数 0.72**

### 3.2 全表校验（`[实测]` 最终审计，脚本 `.scratch/cabling/final_audit.py` + `ladder_audit.py`）

| 校验项 | 命中 | 例外 | 结论 |
|---|---|---|---|
| `R == P × 0.72` | 636 | **0** | 零例外成立 |
| `S == R + Q` | 636 | **0** | 零例外成立 |
| `P == N + O` | 636 | **0** | 零例外成立 |
| `T == ladder(S)` | 636 | **0** | 零例外成立（含非单调 `S=7` 分支） |

**审计口径说明（必须写清，避免"636 还是 638"的疑问）**：

- 扫描到的"有长度块痕迹"行 = **638 行**（比 636 多 2 行）
- 多出的 2 行是 `row332` / `row333`：`Q/R/S 全为空`，仅 `T='待定'` → 是**人工占位标记**而非计算结果
- 因此**可数值校验的有效样本 = 636 行，全部通过，0 例外**

`T` 实测取值集合 `{5, 7, 10, 15, 20, 25, 30}`（只用到前 7 档；后 3 档 `35/40` 是预留档位，从未被 T 触发）
`U` 实测取值集合 `{5, 7, 10, 15, 20, 25, 30, 35, 40}`（9 档，**触及 T 从未用到的 35/40** → 再次证明 U 是人工值）

> **这是本次研究的最高置信度成果**：三列线性关系 + 一列阶梯函数，636 条真实记录零例外。**公式可直接逐字实现，无需近似。**

### 3.3 档位阶梯的精确语义（含 1 个反直觉坑）

| S | T | 说明 |

| 5.00 | 5 | |
| 5.72 | 7 | |
| 6.44 | **10** | ⚠️ 比 S=7 的档位**更大** |
| 7.00 | **7** | `S2=7,7` 单独截住 |
| 7.16 | 10 | 7 < S ≤ 8.5 |
| 8.44 | 10 | |

### 3.5 机内线缆 Q 的取值规则（`[实测]` 636 行）

|---|---|---|---|

### 3.5A 同机柜连线：U 不可由 U 位差推算（`[实测]`，重要避坑）

**这是必须写进文档以免后续走弯路的结论。** 同机柜连线（`N=0 且 O=0`）共 **111 行**：

| 线缆类型 | Q | U | 行数 |
|---|---|---|---|
| LC-LC | 5 | 5 | 33 |
| RJ45 | 7 | 5 | 21 |
| LC-LC | 5 | 10 | 20 |
| RJ45 | 7 | 7 | 18 |
| RJ45 | 7 | 10 | 15 |
| RJ45 | 7 | 15 | 3 |
| LC-LC | 5 | 20 | 1 |

**反例铁证（同 gap、同类型，U 多值）**：

| 类型 | 两设备之间的空 U 数 | U 的取值集合 |
|---|---|---|
| LC-LC | 7 | `[5, 10]` |
| LC-LC | 15 | `[5, 10]` |
| LC-LC | 31 | `[5, 10]` |
| LC-LC | 35 | `[5, 10, 20]` |
| RJ45 | 12 | `[5, 10]` |
| RJ45 | 13 | `[7, 15]` |

> **结论**：同机柜跳线长度是**施工经验选档**，与 U 位间隔**无任何单调关系**（`gap=7` 时 U 有 5 和 10 两种取值，同样 `gap=35` 出现 5/10/20 三种）。

|---|---|

| −1 | **154** |
| 0 | **352** |
| +1 | 76 |
| +2 | 26 |
| +4 | 1 |
| 空值 | 9 |

**按线缆类型拆分**：
| 类型 | U<T（下调） | U==T | U>T（上调） |
|---|---|---|---|
| LC-LC | 41 | 171 | 73 |

> **正确产品语义**：

> - `U` = 设计院实际敷设/采购长度（可读写，是唯一对外生效值）
> - 必须记录 `调整人 / 时间 / 原因 / 原值 / 新值`，并支持把高频调整沉淀为规则

### 3.7 长度计算块的空缺态（`[实测]`，重要业务事实）

V13 布线表 5127 数据行中：
- **636 行有完整长度块**（Q/R/S/T 全有）
- **4491 行无长度块**（Q/R/S 全空，但 U 列有值）

且 `备注1='首期'` 恰好 450 行，可见区数据行恰好 450 行 → **长度计算只对"首期"设备做过，其余是沿用旧值/未复算**。

> **产品启示**：`U` 可以脱离 `T` 单独存在（历史沿用的值）。数据模型必须允许 `U` 有值而 `T` 为空，且**增量重算时不能覆盖这类行**，否则一重算就把历史数据改成 0。

### 3.8 线长计算算法伪代码

```python
# ---- 可配置参数（全部来自实测，但必须外置为配置） ----
CABINET_PITCH_M   = 0.6      # 单机柜等效柜间距(米)
CABLE_SLACK_RATIO = 1.2      # 敷设余量 20%
INTRA_RACK_M = {             # 机内线缆 Q
    "LC-LC": 5.0,
    "MPO":   5.0,
    "RJ45":  7.0,
}
LADDER = [                   # 有序规则表，等价于用户 IFS；顺序即优先级
    ("le", 5.0,  5),  ("le", 6.0,  7),  ("eq", 7.0,  7),
    ("le", 8.5, 10),  ("le", 13.0, 15), ("le", 17.5, 20),
    ("le", 22.0, 25), ("le", 27.0, 30), ("le", 32.0, 35),
    ("le", 37.0, 40),
]

def compute_length(link, cfg):
    q = link.intra_rack_m or cfg.INTRA_RACK_M[link.cable_type]   # Q
    p = link.n_span + link.n_gap                                  # P = N + O
    r = p * cfg.CABINET_PITCH_M * cfg.CABLE_SLACK_RATIO            # R
    s = r + q                                                      # S
    t = None
    for op, limit, out in cfg.LADDER:                              # T
        if (op == "le" and s <= limit) or (op == "eq" and s == limit):
            t = out
            break
    if t is None:
        return Result(length=None, over_limit=True, raw=s)          # S>37 需人工
    return Result(t=t, u=link.override_u if link.override_u is not None else t,
                  p=p, r=r, s=s, over_limit=False)

def recompute_incremental(links, changed_racks, cfg):
    """增量重算：只碰受影响且"曾经算过"的连线"""
    for link in links:
        if not touches(link, changed_racks):
            continue
        if link.t is None and link.u is not None:
            continue          # 历史沿用值，禁止覆盖（见 3.7）
        prev = link.t
        res = compute_length(link, cfg)
        if res.t != prev:
            emit_diff(link, prev, res.t)
            link.t, link.r, link.s, link.p = res.t, res.r, res.s, res.p
            if not link.u_overridden:
                link.u = res.t
```

## 4. N / O 的几何反推（机柜位置 → 跨机柜/间隔机柜）

### 4.0 几何基准：平面图坐标表（`[实测]`，N/O 的唯一正确输入）

**核心发现：N 与 O 必须从「机房平面图」sheet 的行列坐标推导，不能用柜号。** 平面图结构（16 行 × 40 列）：

- `B2:U2 = '404机房（功率4kW/总181架）丝路信息港业务'` → 404 机房的机柜在**列 3..18**（C..R）
- `V2:AN2 = '403机房（功率4kW/总181架）'` → 403 机房的机柜在**列 23..38**（W..AL）
- 通道标签是**竖排合并单元格**：404 房在 S 列（`S3:S4=八通道`、`S5:S6=九通道`、`S7:S8=十通道`、`S9:S10=十一通道`、`S11:S12=十二通道`、`S13:S14=十三通道`、`S15:S16=十四通道`）；403 房在 V 列（`V3:V4=一通道` … `V15:V16=七通道`）
- **每个通道占平面图的 2 行**：上排 = N 侧，下排 = S 侧，格子里的数值就是柜号
- **通道号 → 平面图行号（`[实测]` 精确映射）**：

| 通道 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| 标签起始行 | 3 | 5 | 7 | 9 | 11 | 13 | 15 |
| 所属机房 | 403 | 403 | 403 | 403 | 403 | 403 | 403 |

| 通道 | 8 | 9 | 10 | 11 | 12 | 13 | 14 |
|---|---|---|---|---|---|---|---|
| 标签起始行 | 3 | 5 | 7 | 9 | 11 | 13 | 15 |
| 所属机房 | 404 | 404 | 404 | 404 | 404 | 404 | 404 |

> **关键陷阱**：403 的 ch1-7 与 404 的 ch8-14 **共享同一批行号**（ch1 与 ch8 都从第 3 行开始）。因此 `(通道, 侧别) → 行号` 的映射必须**按机房分段**，不能只按通道号索引，否则 ch1 与 ch8 的几何会互相污染。

- **平面图里每个机柜恰好占 1 列**（不像 U 位点位图每柜占 5 列）→ 这使得 `O = |列差|` 直接成立，无需除以 5
- **镜像重复（`[实测]`）**：位置表 `(通道,柜号) → [(行,列,侧别)]` 共 **362 条，全部是 2 条重复**（如 `(1,1) → [(3,3,'N'), (3,38,'N')]`）。即同一柜号在平面图上有**两个镜像位置**（左右对称），必须用**侧别 + 列坐标**消歧。本项目布线表实际只用其中一侧
- 非机柜占位：`空调`（F/J/N/AA/AE/AI 等列）、`柱子`（`J5:K5`、`J8:K8`、`J11:K11`、`J14:K14`、`AD5:AE5` 等）、`B3:B16='走道'`、`AM3:AN16='走道'`、`T3:U16='空调管道间'`

### 4.1 反推结论（`[实测]` 逐行硬验证）

```python

# N（跨机柜）：全量唯一公式
N = 0 if d == 0 else 4 * d + 4

# O（间隔机柜）：分三类空间关系
# A 类 —— 两柜在同一平面图行（同排、隔通道面对面）：线缆直接横穿通道
O_A = abs(floor_col(本端) - floor_col(对端))

# B 类（同通道跨侧，相邻两行）与 C 类（跨通道）：
```

> **物理含义（这是分层的关键）**：机房的走线架（桥架）只架在**每排的端部**，不在通道中间。所以——
> - **同排面对面**：线缆直接横穿通道，`O = |Δcol|`；
> - **跨侧 / 跨通道**：线缆必须**先沿本排走到排端入口，再从对端排的端部入口折返回来**，所以是两端到排端的**往返距离**。
>
> 这条物理规律一确立，此前观测到的所有"莫名其妙 +5 / +11 / +13 / +17 偏移"全部解释了：它恒等于 `2*CMAX + 1 − (col_a + col_b) − |Δcol|`，本质就是到排端的往返。

- **清洗后 N 值域 = `{0, 8, 12, 16, 20}`**（`15 / 25` 只出现在脏数据行，见 §4.3）

### 4.2 为什么不能用"柜号差"直接算（`[实测]` 教训）

| 尝试 | 命中率 | 结论 |
|---|---|---|
| `O = 柜号差绝对值` | 36.0%（229/636） | 不成立 |
| `O = 柜号差绝对值 + 1` | 7.4%（47/636） | 不成立 |
| `O = ceil(Excel 列差 / 5)`（U 位点位图口径） | 30.7%（195/636） | 不成立 |
| `O = 排内位置索引差` | 45.6% | 不成立（与柜号差同源病） |
| `O = 环形绕行 / 蛇形遍历`（serp/serp2/comb 三变体） | A 类 45.6% / B 类 8.0% | 不成立 |
| `O = 列坐标差绝对值`（A 类） | **93.1%（462/496）** | **成立** |
| `O = 排端折返`（B/C 类） | **B 98.0% / C 60.0%** | **成立** |

- **根因**：柜号在排内是**镜像/折返编号**（403 房 ch1 北侧 c38=柜1、c23=柜13；南侧 c23=柜14、c38=柜27 —— 即柜 1 与柜 27 面对面、2 与 26 面对面），且空调/柱占位使柜号连续而物理位置不连续 → **必须用物理坐标，不能用柜号**
- **为什么平面图列差优于 U 位点位图列差/5**：平面图每柜占 1 列，无取整误差；点位图每柜占 5 列且空调/柱占位造成列序列跳档 → 存在 `ceil` 的边界误差
- **务必记住的坑**：`O = 柜号差 + 1` 这个假设看起来很美（因为 A 类里确实有 47 行对得上），但它**在 636 行上只命中 7.4%**。凡是基于柜号的方案，全部因为它们是在镜像编号上做算术而失败。

### 4.4 两层分离设计（`[设计]`，本报告的核心架构决策）

线长计算必须拆成**几何层（确定性）**与**经验层（需人工确认）**，这是整个模块的骨架：

| 层次 | 字段 | 可复现性 | 校验方式 | 责任归属 |
|---|---|---|---|---|
| **几何层** | `N` ← 平面图行号；`O` ← 平面图列坐标；`P=N+O`；`R=P×0.6×1.2`；`S=R+Q`；`T=ladder(S)` | **确定性，可 100% 复现** | 系统可自动验证，偏差即报错 | 系统 |
| **经验层** | `Q`（按线缆类型的固定档）、`U`（人工核定长度）、跨通道走特殊桥架时的 `N` 例外 | **概率性，需人工确认** | 系统只给建议值 + 差异高亮 | 设计院 |

**这个分离是产品设计的关键**，因为：
1. 几何层可以被系统**完全验证**（同排/跨排几何是客观事实）→ 系统有资格报错、有资格阻止导出
2. 经验层**必须留给人**（施工经验、库存、现场情况）→ 系统只能建议，不能强制
3. 两层分离后，`U≠T` 不再是"算法不准"，而是"经验层人工调整"的正常行为 → 消除用户的信任危机

### 4.5 N/O 建议值算法伪代码

```python
def floor_row(channel, side, geo):
    """通道+侧别 → 平面图行号。必须按机房分段，ch1-7 属 403、ch8-14 属 404"""
    room = geo.room_of(channel)                 # 403 for 1..7, 404 for 8..14
    base = 3 + 2 * ((channel - 1) % 7)          # 实测: 3,5,7,9,11,13,15
    return base + (0 if side == "N" else 1)

def suggest_no(link, geo):
    a = geo.floor_pos(link.local_channel, link.local_rack, link.local_side)
    b = geo.floor_pos(link.peer_channel,  link.peer_rack,  link.peer_side)
    d = abs(floor_row(a.channel, a.side, geo) - floor_row(b.channel, b.side, geo))

    if d == 0:                                   # 同排
        return Suggestion(n_span=0,
                          n_gap=abs(a.col - b.col),      # 平面图每柜 1 列
                          confidence="high")
    else:                                        # 跨排
        return Suggestion(n_span=4 * d + 4,              # 实测系数
                          n_gap=UNKNOWN,                 # 跨排 O 走排端折返公式；C 类低置信强制人工
                          confidence="high",
                          needs_manual_gap=True)

def audit_no(link, suggestion):
    """产品卖点：自动检出源数据错误"""
    if link.n_span != suggestion.n_span:
        return AuditFinding(
            level="warning",
            code="N_MISMATCH",
            message=f"跨机柜 N={link.n_span}，几何推导应为 {suggestion.n_span}（"
                    f"平面图行差 {suggestion.d_row}）",
            hint="疑似 N/O 互换或漏填跨排",
        )
    if suggestion.n_gap is not UNKNOWN and link.n_gap != suggestion.n_gap:
        return AuditFinding(level="warning", code="O_MISMATCH", ...)
```

> `[已定论]` 跨排的 `O` **有公式** —— 不是柜号函数，而是**到排端走线架入口的折返距离**：`O = (CMAX[a]-col_a) + (CMAX[b]-col_b) + 1`，`CMAX[403]=38`、`CMAX[404]=18`。B 类（同通道跨侧）98.0%、C 类（跨通道）60.0%。这是排端走线架的物理拓扑决定的，不是拟合。**C 类 40 行里有 16 行集中等在核心交换机上联口，属人工判断差异 → 产品应给建议值 + 低置信度标注 + 强制人工确认**。（早期版本在此写"无稳定公式，最好 19.3%"，是尚未发现排端折返规律时的结论，已作废。）

### 5.2A 图模型与最短路算法（`[设计]`）

**图建模**：

```
节点（Node）：
  机柜顶出线点 (rack_top)      —— 每机柜 1 个
  桥架转角/分支 (tray_junction)
  进线口 (entry)

边（Edge）：
  机柜顶 → 所属列头柜/列间桥架   weight = 垂直落差 + 水平偏移
  桥架段 - 桥架段（junction）    weight = 该段实际长度
  桥架 - 目标机柜顶              weight = 垂直落差 + 水平偏移

边权 = 物理长度（米），并按策略加权：
  w(e) = len(e) × (1 + penalty_kind(e))    # 光纤走强电桥架 penalty 大
```

**算法选型**：

| 算法 | 复杂度 | 适用 | 本项目判断 |
|---|---|---|---|
| **Dijkstra**（堆优化） | `O(E log V)` | 单源最短路，非负权 | ✅ **首选**：桥架图规模小（V≈200 节点、E≈400 边），单次 < 1ms |
| **A\*** | `O(E log V)`，常数更小 | 有可采纳启发式（欧氏距离） | 可选：批量算 5127 条时比 Dijkstra 快约 2–5 倍 |
| **Floyd-Warshall** | `O(V³)` | 全源最短路 | ⚠️ `V=200 → 8×10⁶`，**预计算一次全源表**反而最优（5127 次查询变成 O(1) 查表） |
| BFS/DFS | `O(V+E)` | 无权图 | ✗ 需要长度，不适用 |

> **工程结论**：**预计算全源最短路表**（`V≈200`，Floyd `8×10⁶` 次操作，约 0.1–0.5s，可缓存），之后每条连线查表 `O(1)`。这是本项目规模下的最优解 —— 比 5127 次单源 Dijkstra 更简单也更快。
> 若未来桥架节点数增长到 `V>1000`（`V³=10⁹` 变慢），则切换为 A* 按需计算。

**路径复用与线束统计**：

```python
def bundle_report(links, tray_graph):
    """输出每条桥架段的线缆数量/截面积占比，用于容量校验（规则 C25）"""
    load = defaultdict(int)
    for link in links:
        for seg in tray_graph.path(link):
            load[seg.id] += link.cable_count      # 同一路径 N 条线
    for seg, n in load.items():
        yield TrayLoad(seg, count=n, fill=n * seg.unit_area / seg.capacity)
```

```python
def assign_server_ports(server_group, access_switch, geo):
    """
    遍历顺序：机柜顺序（通道→排→柜号） → 柜内 U 位从高到低 → 端口号连续递增
    """
    port_no = 1
    for rack in sorted(server_group.racks, key=geo.rack_order):
        # 柜内槽位：U 从高到低（31-32 → 3-4）
        for slot in sorted(rack.server_slots, key=lambda s: -s.start_u):
            server = slot.server
            # 该服务器在此交换机上占 1 或 2 个端口
            for nic in server.nics_mapped_to(access_switch.role):
                yield Assignment(server=server, nic=nic,
                                 slot=slot, switch_port=f"10GE1/0/{port_no}")
                port_no += 1
```

### 7.6 算法选型：从"连接意图"到"具体端口配对"

**问题形式化**：给定
- 一组设备（含各自的端口清单、机柜位置、U 位）
- 一组**连接意图**（如"每台计算节点A 的 `万兆1` 接业务接入交换机(业务) 的某个 10G 口"）
- 一组**约束**（端口唯一、两端速率一致、冗余对不共用同一台交换机、端口优先连号、同机柜优先）

求：一个**连线集合**（本端设备+端口 ↔ 对端设备+端口），使约束全满足且端口分配符合设计院习惯。

**四种候选算法对比**：

| 算法 | 思路 | 时间复杂度 | 能保证最优？ | 能否表达"端口连号偏好" | 适合度 |
|---|---|---|---|---|---|
| **A. 确定性顺序分配**（实测用户的人工做法） | 按机柜顺序 → 柜内 U 位从高到低 → 端口号递增，逐个 yield | **O(n)** | 不需要（唯一解） | 天然满足（端口就是递增分配的） | ★★★★★ 首选 |
| **B. 贪心 + 启发式打分** | 每步选"当前最优"的 (设备, 端口) 对 | O(n·m·log m) | 否 | 需要把偏好编码成权重函数 | ★★★ 备选 |
| **C. 二分图最大匹配**（Hopcroft-Karp） | 左 = 意图，右 = 端口；边 = 合法配对 | **O(E√V)** | 最大化匹配数（= 接线数量） | **无法表达**（匹配不关心"哪个端口更合适"） | ★★ 仅用于可行性检查 |
| **D. 最小费用流**（MCMF / SSP） | 源→意图→端口→汇；费用 = 违反偏好的惩罚 | **O(F·E·log V)** 或 SPFA 更慢 | 是（最小总费用） | **能**（费用函数可编码连号、跨柜、堆叠口限制） | ★★★★ 当约束冲突需最优折衷时 |

**选型结论（分场景）**：

```python
def build_patch_panel(intents, devices, policy):
    """
    场景判定 → 算法选择。绝大多数真实场景走路径 1。
    """
    # ---- 路径 1：结构良好（拓扑树 + 端口容量充足）→ 确定性顺序分配 ----
    # 实测依据：用户 5127 行数据里 81% 的 (本端设备,对端设备) 分组端口完全连续
    if is_tree_topology(intents) and has_enough_ports(intents, devices):
        return deterministic_assign(intents, devices, policy)   # O(n)

    # ---- 路径 2：有冲突但可局部修复 → 贪心 + 回溯 ----
    if conflict_ratio(intents, devices) < policy.repair_threshold:
        return greedy_with_backtrack(intents, devices, policy)

    # ---- 路径 3：需全局最优（如预算约束下最小化线材）→ 最小费用流 ----
    return min_cost_flow(intents, devices, policy)
```

**为什么"确定性顺序分配"是首选（`[实测]` 三重铁证）**：

1. **用户实际就是这么做的**：`计算接入交换机(业务)-1` 的端口 `1..44` 严格对应 ch2 的 r1..r6 的 8 个槽位（每柜 8 槽，`44 = 5.5 柜 × 8`），端口号随机柜遍历连续递增
2. **端口连续率 81%**：按 `(本端设备, 对端设备名称)` 分组的 332 组中，269 组端口完全连号；不连号的 63 组全部是"某设备只接了部分端口"或端口 48 单列（堆叠口）→ 说明**默认行为就是顺序分配**
3. **核心交换机成对分配**：`port = 2*(k-1)+1, 2*(k-1)+2`，`k` = 上联设备在有序列表中的序号 —— 也是确定性顺序算法

> **复杂度对比**：`n` = 连线数（本项目 5127）。路径 1 是 `O(n) ≈ 5千次操作`，路径 3 的 MCMF 在 `n=5000`、端口候选 `m≈50万` 时约 `O(5000 × 50万 × log) ≈ 10^10` 量级 → **慢 6 个数量级，且没有任何收益**（因为真实数据里根本不需要"最优折衷"）。
> **结论：默认路径 1，MCMF 只作为"约束冲突时的兜底"，不作为主算法。**

### 7.6A 数据结构：端口资源池（`[设计]`）

端口分配的性能瓶颈是"查找可用端口"，必须用索引而非线性扫描。

```python
class PortPool:
    """
    端口资源池。目标：单端口查询/占用 O(1)，按条件筛选 O(log n)。
    关键设计：三级索引 + 免费链表，避免每次遍历全部端口。
    """
    def __init__(self, ports):
        self._by_id      = {p.id: p for p in ports}          # O(1) 主键
        # 二级索引：按 (设备, 速率) 分组 -> 有序端口列表（按 port_index 排序）
        self._device_rate = defaultdict(list)
        # 三级索引：按 (设备, 速率, 已用/空闲) 维护"最小可用端口"堆
        self._free_heap   = defaultdict(list)
        for p in ports:
            k = (p.device_id, p.rate)
            self._device_rate[k].append(p)
            if p.is_free:
                heapq.heappush(self._free_heap[k], (p.port_index, p.id))
        for lst in self._device_rate.values():
            lst.sort(key=lambda p: p.port_index)

    def acquire(self, device_id, rate, policy) -> Port:
        """分配一个端口。policy 决定"优先连号"还是"优先低成本"。"""
        k = (device_id, rate)
        heap = self._free_heap[k]
        while heap:
            idx, pid = heapq.heappop(heap)
            p = self._by_id[pid]
            if p.is_free:                        # 惰性删除：堆里可能有已占用的
                p.mark_used()
                return p
        raise PortExhausted(device_id, rate)

    def release(self, port):                     # 增量重算时回滚用
        port.mark_free()
        k = (port.device_id, port.rate)
        heapq.heappush(self._free_heap[k], (port.port_index, port.id))

    def reserve_block(self, device_id, rate, start, end, reason):
        """预留端口段（实测：接入交换机保留 45/46/47，48 为堆叠口）"""
        for p in self._device_rate[(device_id, rate)]:
            if start <= p.port_index <= end:
                p.reserve(reason)
```

> **`[实测]` 依据**：接入交换机的 `10GE1/0/1..44` 给服务器、`45/46/47` 保留未用、`48` 作堆叠口（`10GE1/0/48` 出现 27 次）；核心交换机端口按 `2(k-1)+1, 2(k-1)+2` 成对分配 → 这两类"预留 + 成对"规则必须能在 `PortPool` 上以 `reserve_block` / `acquire_pair` 表达。

### 7.6B 增量重算（避免全量重跑的工程必需）

**`[实测]` 真实场景就是增量的**：636 行有长度块、4491 行无（历史沿用），备注 `'首期'` 恰 450 行 → 用户是"每次加一批设备、重算这批"的工作方式。

```python
def incremental_recompute(changed_links, all_links, cfg, geo):
    """
    只重算受影响的行。三类影响面：
      1. 自身字段变了 → 重算自身
      2. 本端/对端设备换了机柜/U位 → 重算所有与该设备相关的行
      3. 几何参数（pitch/slack/ladder）变了 → 全量重算（无法局部化）
    """
    dirty = set(l.id for l in changed_links)

    # 影响面扩展：设备位移会波及它的所有连线
    moved_devices = {d for l in changed_links for d in (l.local_dev, l.peer_dev)
                     if d in l.changed_fields.get("position", set())}
    if moved_devices:
        dirty |= {l.id for l in all_links
                  if l.local_dev in moved_devices or l.peer_dev in moved_devices}

    # 参数变更 → 全量
    if cfg.geometry_changed_since(last_run):
        dirty = {l.id for l in all_links}

    # 保护历史沿用值（风险 R4 的实现）
    result = []
    for l in all_links:
        if l.id not in dirty:
            continue
        if l.t is None and l.u is not None:      # 历史行，不动
            result.append(Skip(l, reason="HISTORICAL_U"))
            continue
        result.append(recompute(l, cfg, geo))
    return RecomputeResult(result, dirty_count=len(dirty))
```

**幂等性要求**：`recompute(l)` 必须是纯函数（`f(link, cfg, geo) → link'`），不依赖执行顺序、不依赖上一次结果 → 这样同样的输入重算 N 次结果相同（配合 §9A 的幂等导入）。

### 9.2 校准方法（用历史数据反哺）

```python
def calibrate_from_history(links_with_u, cfg):
    """
    用人工核定值 U 反推最优参数。
    思路：给定 U，约束是 ladder(S(P(N,O),Q)) <= U，求使预测最贴近的参数。
    """
    # Step 1: Q 校准（最独立，先做）
    for ctype, group in group_by(links_with_u, "cable_type"):
        cfg.INTRA_RACK_M[ctype] = mode(g.u_implied_q for g in group)

    # Step 2: 阶梯档位校准（T 已知时零成本）
    # 验证 ladder 是否与历史一致；不一致的档位进"待确认"清单

    # Step 3: pitch × slack 联合校准
    # 对每个 (N,O) 已知的样本，s = pitch*slack*P + Q
    # 用最小二乘拟合 k = pitch*slack
    k = least_squares_fit([(l.p, l.s - l.q) for l in links_with_u])

    # Step 4: 输出校准报告（哪些参数的调整改变了多少行）
    return CalibrationReport(prev=cfg.snapshot(), new=cfg, impacts=...)
```

**实测可校准性验证**：`k = 0.72` 在 636 行上零例外 → **本项目不需要校准，直接采用**。校准机制是为其他项目准备的（不同机房柜间距可能不同）。

## 9A. 幂等导入：无自然主键连线的 diff / merge 设计

### 9A.1 问题：连线表没有自然主键（`[实测]`）

一条连线的"业务身份"是什么？候选键都不完美：

| 候选键 | 唯一性 | 问题 |
|---|---|---|
| 行号 | ✗ | 用户插入/删除一行即全部漂移 |
| 本端端口 `(设备, 通道, 柜, U, 端口)` | `[实测]` **5127 行零重复** ✓ | 但设备重命名或换柜后失效 |
| 对端端口 `(通道, 柜, U, 端口)` | `[实测]` **1 处重复**（row321/322/323，分线接入交换机-1 5U37U → 分线接入交换机-2，端口 `25GE1/0/48` 与 `100GE1/0/7`/`100GE1/0/8`） | 上行冗余对的端口命名不严谨，不能单独做主键 |
| 两端端口对 | 依赖上面两者 | 跨柜时对端 U 位可能为空（4230 行对端设备名为空） |

> **结论：单一字段都不能做主键，必须用"复合业务键 + 稳定代理键"双轨制。**

### 9A.2 方案：三段式稳定业务键（`[设计]`）

```python
def stable_link_key(link, site_key):
    """
    稳定业务键 = 站点 + 本端端口身份 + 对端端口身份（对端可缺省）
    设计原则：优先用"物理位置"（最稳定），退化用"设备名+端口名"
    """
    local = (
        "L",
        normalize(link.local_device_name),    # 去空格、去括号后缀差异
        link.local_channel,
        link.local_rack,
        normalize_u(link.local_u),            # '3-12U' → (3,12)
        normalize_port(link.local_port),      # '10GE1/0/1' → '10GE-1-0-1'
    )
    peer = (
        "P",
        normalize(link.peer_device_name) if link.peer_device_name else None,
        link.peer_channel,
        link.peer_rack,
        normalize_u(link.peer_u) if link.peer_u else None,
        normalize_port(link.peer_port) if link.peer_port else None,
    )
    return hash64(site_key, local, peer)
```

**关键设计点**：

| 设计点 | 做法 | 理由 |
|---|---|---|
| **规范化的位置优先** | 键里含 `通道/柜/U/端口`，不含"行号/设备实例 ID" | `[实测]` 位置信息在用户数据里最稳定；行号会漂 |
| **端口名归一** | `10GE1/0/1` 与 `1/0/1` 归一为 `(10GE,1,0,1)` 与 `(-,1,0,1)`，用**速率+槽+口**三元组 | `[实测]` 同一设备左右双栏写法不一致（`11+12冷通道/连线表`） |
| **U 位归一** | `3-12U`→`(3,12)`；`40U`→`(40,40)`；`'设备自带'`→`None`（sentinel） | `[实测]` 13 种 U 写法格式统一 |
| **设备名归一** | trim + 全角括号转半角 + 去尾随空格 | `[实测]` `带外交换机 1`（尾随空格，76 行）≠ `带外交换机1` |
| **对端可缺省** | 对端为空的 4230 行，键退化为"仅本端" | `[实测]` 对端设备名为空是合法预留状态 |
| **碰撞处理** | 键碰撞时用 `(key, occurrence_index)` 二级键 | `[实测]` 对端端口有 1 处重复 |

### 9A.3 三路 diff 算法（import 时的核心逻辑）

```python
def import_diff(existing: list[Link], incoming: list[Link]):
    """
    三路分类：UNCHANGED / UPDATED / ADDED / REMOVED / MOVED
    幂等性保证：同样的输入文件导入 N 次，结果与导入 1 次相同
    """
    index = {stable_link_key(l): l for l in existing}
    seen, added, updated, unchanged = set(), [], [], []

    for inc in incoming:
        k = stable_link_key(inc)
        if k in seen:                       # 文件内部重复行
            yield Finding("DUPLICATE_IN_IMPORT", inc, level="warning")
            continue
        seen.add(k)

        old = index.get(k)
        if old is None:
            # 键不存在 → 尝试"移动/改名"识别（见 9A.4）
            old = find_moved(inc, index, exclude=seen)
            if old is not None:
                updated.append(LinkDiff(old, inc, change="MOVED"))
                continue
            added.append(inc)
        elif deep_equal(old, inc, ignore_fields=("row_no",)):
            unchanged.append(inc)
        else:
            updated.append(LinkDiff(old, inc, change="UPDATED"))

    removed = [l for k, l in index.items() if k not in seen and k not in moved_keys]
    return ImportResult(added, updated, removed, unchanged)
```

### 9A.4 "移动/改名"识别（避免删了重建）

设备换柜、改名会让业务键变化，若直接当"删+增"处理，会**丢掉所有人工核定的 `U` 值和调整留痕**。因此需要软匹配：

```python
def find_moved(inc, index, exclude):
    """
    二级匹配：同本端设备名 + 同端口名，但位置变了 → 判为 MOVED
    三级匹配：同端口名 + 同对端 → 判为候选，需人工确认
    """
    # 二级：设备名 + 端口
    cands = [l for k, l in index.items()
             if k not in exclude
             and normalize(l.local_device_name) == normalize(inc.local_device_name)
             and normalize_port(l.local_port) == normalize_port(inc.local_port)]
    if len(cands) == 1:
        return cands[0]

    # 三级：端口 + 对端（设备名变了）
    cands = [l for k, l in index.items()
             if k not in exclude
             and normalize_port(l.local_port) == normalize_port(inc.local_port)
             and normalize_u(l.peer_u) == normalize_u(inc.peer_u)]
    if len(cands) == 1:
        return cands[0]          # 标为 MOVED 但标记 needs_review
    return None
```

**MOVED 时的字段继承规则**：

| 字段 | 处理 |
|---|---|
| `U`（核定长度） | **继承原值**（人工劳动成果不可丢） |
| `Q`（机内线缆） | 按新线缆类型重算（若类型没变则继承） |
| `N / O / P / R / S / T` | **全部重算**（位置变了，几何层必须重算） |
| 调整留痕 | 追加一条 `MOVED` 记录，保留完整历史 |

### 9A.5 幂等性验证用例（验收必测，`[设计]`）


### 9A.6 导出侧的幂等要求

- **导出必须是原文件的超集/等价**：25 列同名同序，未修改的行**位级不变**（包括 `0.72` 的浮点表示）
- **不重排行序**：保留用户原始行序（`row_no` 只作排序提示，不作业务键）
- **不擅自取消隐藏**：V13 有 4682 隐藏行 + 4 隐藏列（A/G/N/T），导出时默认**保持原隐藏状态**，另提供"全展开"选项
- **公式 vs 值**：提供两个导出模式 —— `formula`（写回 Excel 公式，用户可继续手算）与 `value`（写死数值，防误改）

## 10. 技术风险清单（按严重度排序）

| # | 风险 | 严重度 | 说明与缓解 |
|---|---|---|---|
| R1 | **N/O 无法 100% 自动推导** | 高 | N 98.6%（627/636）；O 分层 91.8%（A 同排 93.1% / B 同侧跨排 98.0% / **C 跨通道仅 60.0%**）。缓解：几何建议 + 人工覆盖 + 置信度标注（A 高 / B 极高 / C 低）；同时把偏差转成"数据审计"能力（见 §4.3）。**换机房时 CMAX 与"走线架只在排端"的假设可能失效，是 v1.0 通用化的首要验证项** |
| R2 | **阶梯公式非单调** | 高 | `S=7→7` 但 `6.44→10`。若产品"顺手优化"成单调函数，导出值与用户 5127 行历史对不上。缓解：逐字复现 + 回归测试锁定 |
| R3 | **U（核定长度）双向调整且下调更多** | 高 | 172 下调 vs 103 上调。若设计成"只能上调"，用户会觉得系统算得偏高。缓解：双向可编辑 + 强制填原因 |
| R4 | **历史沿用值不可被覆盖** | 高 | 4491 行 U 有值但 T 为空。增量重算若覆盖会批量篡改历史。缓解：`T is None and U is not None` 时跳过 |
| R5 | **点位图与布线表粒度不一致** | 中 | 点位图 39 类标签 vs 布线表 192 台设备，交集仅 27。缓解：两视图独立建模 + 按机柜/通道关联，不假设设备名一一对应 |
| R6 | **5 种连线表版式 + 表头自身漂移** | 中 | 双栏版式表头重复、端口写法不一致。缓解：模板+别名驱动，保留原始文本 |
| R7 | **脏数据与 sentinel 文本** | 中 | `25G-SR` 填进间隔机柜、`设备自带`/`待定` sentinel、`带外交换机 1` 尾随空格。缓解：隔离错误表 + trim + 别名归一 |
| R8 | **无桥架数据，无法验证路径模型** | 中 | 用户数据完全没有桥架。缓解：Level 1 经验公式为默认，Level 2 可选 |
| R9 | **空调/柱位置每通道不同** | 中 | ch1 空调 c28/c47/c67，ch8/9 c23/c43/c62。硬编码会错。缓解：位置参数表落库 |
| R10 | **耗材清单与布线表不同源** | 低 | 需求数量 ≠ U 列 GROUP BY（仅 5/24 行吻合）。缓解：不把两者当同一数据源，各自独立计算 + 差异报告 |
| R11 | **连线无自然主键，导入易重复/丢数据** | 中 | 单一候选键均有缺陷（见 §9A.1）。缓解：三段式稳定业务键 + MOVED 软匹配 + 幂等测试用例（§9A.5） |
