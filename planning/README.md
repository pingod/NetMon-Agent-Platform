的 3U」—— 现场按旧表插线全插错口。这一版让每次拖动都返回影响面并在界面上说出来，同时给一步撤销（撤销本身也是一次移动，没有撤销就等于再改 91 行）。顺带修掉一个同类的真 bug：单台路径缺了 v0.11 给批量加的那道名字白名单，于是「拖一台不存在的设备」会被解析成该 U 位上那台真机并**成功挪动它**，返回 `ok=true`，界面上看不出任何异常 —— 而同样的动作走批量接口会被正确拒绝。v0.11「整摞挪」—— Shift 点选多台后拖动任意一台，**整组一起平移同样的格数**（跨机柜时整组换柜并保持各自 U 位）。设计上没有引入框选：框选与拖拽在前 100ms 完全无法区分，用户想选 3 台结果动了其中一台；Shift 点击没有这个歧义。批量语义是「同一个相对位移」而不是各自给新 U 位 —— 现场动作是「这一摞往下挪 8 格」，逐台指定新位置要用户手算保持间距，算错就是设备叠一起。这条限制不是性能考虑而是**正确性**：8 台整体下移一格时每台的新位置恰好是下一台的旧位置，逐台校验会让第 1 台看到第 2 台还站着，一台都动不了。顺带修掉一个会**挪错设备**的真 bug：布局段设备的实例名匹配不上时，反查会退回「按型号 + U 位找第一台」，于是「不存在的设备」被当成那台真设备，批量拖动会真的动了用户没选中的机器。v0.10「挪得动」—— U 位图上 827 台设备可以**跨机柜**拖动（此前只能柜内调 U 位）。三类设备三条写入路径：布局段排布（663 台）写位置覆盖记录、逐台声明（164 台）直接改 `rack`、7 台源数据自相矛盾的无处可改。跨柜只换柜不换 U（平面图一格没有「第几 U」，硬猜等于替用户做他没表达的决定）；跨通道拒绝并说清那是重规划。顺带修掉一个真 bug：原先两类设备共用「目标柜必须在布局段里」这条检查，而 ch1（网络/安全机柜区）**一段布局都没有**，导致核心交换机一台都换不了柜。更早的 v0.9「印得出来」已落地 —— 四种交付物里最后缺的**线缆标签清单**补齐了：10254 张标签（每根线两端各一张），格式从真实示例表反解（`11A14-39U ## 一、一句话说清这个产品要解决什么

现在这份 5127 行的《设备上架规划》Excel，是靠**人读平面图数格子、手填公式、六个版本反复改**做出来的。它有一个致命的隐性事实：

**5113 条有效连线里，只有 636 行（12.4%）真的走了公式链；剩下 4477 行（87.6%）连 N/O/P 都没填，长度是人凭经验直接敲进去的。**

所以这个产品不是"把 Excel 搬到网页上"，而是要做三件 Excel 做不到的事：

| # | 能力 | 现在怎么做 | 系统怎么做 |
|---|---|---|---|
| 1 | **几何自动化** | 人对平面图数格子算跨机柜/间隔机柜 | 从平面图反解出坐标模型，`N` 公式 98.6% 可复现、`O` 分三类 91.8% 可复现 |
| 2 | **布线表生成** | 5113 行逐行填，每改一次布局全表重来 | 目标：填约 30 行「接线意图」→ 自动生成 5113 行（端口分配规律已验证 3850/3850 = 100%，**v0.2 尚未接通生成入口**，见 §8.2） |
| 3 | **数据体检** | 不知道表里哪儿错了 | 自动检出 52 处几何填错、13 对 U 位重叠（含 4 对真撞车）、3771 行缺几何量、49 行 IFS 缝隙多买一档 |

### 7.0a 交付形态（v1.0，Q3 拍板：双形态、绿色包为默认）


**绿色包 = 解压即用的跨平台目录**（Linux x86_64 + Windows x64 同一个包）：

| 成员 | 内容 |
|---|---|
| `runtime/linux/` + `runtime/windows/` | 嵌入式 CPython 3.12.11（python-build-standalone，**钉死 tag+sha256**） |
| `vendor/python/` | 全部第三方依赖，双平台二进制合并共存（*.so 与 *.pyd 文件名不冲突） |
| `backend/` + `web/dist/` + 源数据 | 与仓库同布局（`parents[3]` 定位源文件/数据的路径逻辑不能破坏） |
| `run.sh` / `run.bat` | 现场唯一需要的动作：双击/执行，开 `http://127.0.0.1:8000` |
| `自检.sh` | **AC-8 的验收动作**：解释器 → 依赖 → 导出铁线 → 起服务探测，全程零网络 |

现场（断网跳板机）：
`tar xzf … && cd … && ./run.sh`（Windows 双击 `run.bat`），验收跑 `./自检.sh`。

**为什么 venv 不可打包**：venv 全是绝对路径与平台绑定物，拷走必坏。所以包里
放的是**可重定位的 standalone 解释器 + site-packages 目录 + PYTHONPATH**，
现场不执行任何 `pip install`。实测自检时把 `http(s)_proxy` 指向死端口模拟断网，
两轮连跑全过、无残留进程。

**Docker 形态②**（客户 IT 允许时）：`docker compose up -d --build`。
本机真实构建 + 起容器验证过：`/api/meta` 5127 行、`/api/scene` 362 柜、
HEALTHCHECK healthy、数据卷持久。`PIP_INDEX_URL` build-arg 应对 pypi 限速。

## 八、v0.3 已完成（接线意图 → 布线表 + 耗材清单）/ 下一步

### 核心突破：破解了「接线意图」的真实结构

整个 v0.3 的难点不是写代码，是**搞清楚人做这份表时到底按什么规则接线**。
过程中证伪了 4 个模型（区间展开 10.9%、`(型号,网口,交换机)` 组合 27.7%、
严格计算节点区间 6.2%、纯 `(机柜,槽位)` 升序 82.55%），最终得到三条规则：

| 规则 | 内容 | 不加这条时的命中率 |
|---|---|---|
| **柜内相位轮转** | 通道内机柜升序，柜内按 `(slot − carry % 8) % 8` 升序（`carry` = 前序机柜设备数累计） | 82.55% |
| **重复槽位顺延整轮** | 同柜同槽位第 k 台排序键 = `k × 8 + 轮转序号`，必须顺延一整轮 | 95.64% |
| **连续切块 + 末台吸收余量** | 前 K−1 台各装 `capacity`（实测 44），末台吃剩余全部（可超容量） | 96.17% |

配上这两条边界事实后达到 **100.00%（3850/3850 计算节点行）**：
- **容量挂在「端口面」上，不在整机**：`存储接入交换机-1` 整机 max 48 口，但 `25G1` 面只有 40 口
  （`25GE1/0/48`/`100GE1/0/7|8` 是上行口）。写整机 max 会让 `[40,40,36]` 变成 `[48,48,20]`，全盘错位。
- **交换机必须按「网口」拆分链路**：`ch2` 的 10 台业务接入交换机里 `-1/-3/-5/-7/-9` 接 `万兆1`，
  `-2/-4/-6/-8/-10` 接 `万兆3`。只按 `(通道, 型号)` 建链会把 10 台混成一条，命中率从 100% 掉到 **14.09%**。

还有一条**产品必须告诉用户的诚实边界**：`4430/4562 = 97.11%` 的行可由规则生成，
剩下 132 行是特殊机型（网络功能服务器/防火墙/管理节点/GSO/密码机等），
**每台一种接法，规则推导不出来**，必须在意图里显式声明连线。

### 与真实 V13 的对账结果（可复现的验收）

```
意图 949 行  →  生成 5127 行  （×5.4）

行位对齐    5127 / 5127     多出 0     缺失 0
长度比对    578 / 636 = 90.9%（公式链在人工输入一致时 100% 复现）
```

**长度的 55 处差异必须这样理解**（这也是界面上一比一展示的口径）：

| | 结果一致 | 结果不同 |
|---|---|---|
| **人工 N/O/Q 与几何一致** | **578** ← 公式链 100% 可信 | **0** ← 一格都不许有 |
| **人工 N/O/Q 与几何不一致** | 3（凑巧抵消） | **55** |

`578 + 3 + 55 = 636` 精确闭合。真实表里只有 **P/R/S/T 是公式**，
`N/O/Q` 三列是**人手填的**（实测 P/R/S/T 各 636 个公式格，N/O/Q 公式 0 格）。
所以「公式准不准」必须先对齐输入才能问：输入一致时 **578/578 全中**。

那 55 行差异的成因全部可归因，且**刻意不去对齐** —— 悄悄对齐等于把源数据的
录入错误固化进算法，下一套机房会照抄这个错：
- `业务核心交换机-1 → ch1-r6` 人填 O=7（几何 6）、`→ ch1-r22` 人填 O=6（几何 7），**两组恰好互换**
- `计算接入交换机(存储)-2 → r4/r5` 的 O 填成 `0/1` 而几何是 `1/0`，**同柜与邻柜判定填反**

### ② 页面内意图编辑器

浏览器里直接改 949 行意图，不用回 Excel。六段页签（布局/交换机/特殊设备/路由/交换机组/显式连线）+
受控输入框，改一格即时校验、保存成新版本、上面的布线表立刻重算。

`domain/ports/intentcheck.py` 查的是**意图**（949 行，人写给程序的），

- `SW_MODEL_EMPTY` 是**条件严重度**：真实意图里「带外交换机-2」型号为空，

  所以进链时 error、否则 warn。
- `POSITION_TAKEN` 是 warn 不是 error：原表本来就有 6 处 U 位叠放
  （`tgw-1` 与 `tpgw-1`、备份机与备份一体机），属规划占位不是错。

测试里锁住一个容易误判的语义：**链只有一台交换机时 `capacity` 不起作用**。
生成器规则是「前 K−1 台各吃 capacity，最后一台吸收全部余量」，
所以单块链会把该 `(通道,型号,网口)` 的所有节点都接到这一台 ——
加一台交换机 + 一条单块链，增行是通道 2 全部 96 台计算节点A，不是 capacity 的 8。
这也正是真实意图每条链都声明 5 台的原因：一台 ToR 接不下 96 台。

AG Grid Community 缺剪贴板复制粘贴/区域选择/填充柄（Enterprise $999/dev，离线部署还要再买授权）。
自研 `domain/ports/clipboard.py`（667 行）+ 三个端点，四件能力齐了：

| 能力 | 端点 | 说明 |
|---|---|---|

真正需要「从 Excel 粘 50 行进去」的是 949 行的意图六段表格。

**三个设计决定（都是踩过坑之后定的）**：

- **两个端点都收 `doc`，不自己读磁盘/库**。编辑器里是本地草稿 —— 用户改了 10 格还没保存。
  端点若自己读文件，复制出去的是「上次保存的版本」，而用户看到的是刚改的内容。
  这种「复制了但内容不是眼前这份」的错极难发现，因为文本看起来也很像。
- **TSV 转义与填充规律都只在后端有一份实现**。前端拼一份、后端拼一份，迟早
  「复制出去粘回 Excel 少一列」「拖 5 格填出 4 格」。`format_for_clipboard` 与
  `parse_clipboard` 是一对逆运算，往返恒等有单测守着。
- **单格 Ctrl+C 放行给浏览器**。跨多格才接管 —— 用户双击一个长设备名只想复制这串文字，
  此时抢过来会复制到整个格子的值，反而更糟。

**选区数学抽成 `web/src/store/selMath.ts` 单独成模块**：它是「拖出来的框」到
「真正被复制/填充的区域」之间唯一的换算点。这几行逻辑的错法都很隐蔽 ——
框看着是对的，实际范围缩成一格或镜像到另一侧，用户在界面上看不出问题，
直到复制少了两列。而它又只能靠手点验证（拖动事件），所以抽出来才测得动（19 例）。

### ④ 2D SVG 施工图导出（FR-6.7）

`domain/exporting/svg.py` + `GET /api/draw/racks.{svg,html}`。图纸是唯一会离开屏幕的东西 ——
界面画错用户当场能改，图纸画错是印出来贴到机柜门上之后才发现。四条硬约束：

### ⑥ 多项目 / 版本对比（V8→V13 六版 Excel diff）

`domain/exporting/stockdiff.py` + `infrastructure/xlsx/stock_reader.py` +
`application/services/compare.py` + 三个 API + 第八页签「版本对比」。

三条实测决定了整个设计：

**1. 五版「连线表(不含长度)」逐行完全相同。** V8（2026-06-07）到 V13（2026-07-14）
五个星期，5110 行里一个格都没动 —— 是死文件。所以下拉排序把当前布线表排 0、
无长度那版排 3、存档排 9。混在一起会让用户第一次就选到它、得到「完全一致」、以为功能坏了。

**2. V13 的真实改动不是「改了接线」。** V12 布线表 ≡ V13「布线表（旧）」逐行完全一致。
V13 干的三件事：把 V12 原样归档、补齐「本端设备名称」列（14%→100%）、删掉 4 条连线（5131→5127）。
补一列名字按行比会得 **4400 条假「修改」** —— 所以填充率变化单独一块显示，不混进「修改了 N 行」。

**3. 行级差异会骗人，必须做设备级聚合。** V12→V13 按位置键（含 U 位）比对：
**4886 新增 / 4890 删除**。真相是同一批交换机整体挪了 1U —— 一台交换机 44 根线挂在同一个 U 位上，
U 一变按行比就是 44 条新增 + 44 条删除，实际一根线都没换。

所以加了设备级聚合（键 = 通道 + 机柜 + U 位，同柜内按端口集合重叠度贪心匹配）：
**56 台挪了 U 位 / 2 台新增 / 0 台移除 / 54 台端口有变**。两个数字同屏 + 一句解释，用户才理解差距。

比对键三层（`strict` 实例名精确 / `loose` 对端用型号+位置 / `position` 纯位置），
由后端按**前提条件**（该层字段两侧填充率都 ≥50%）降级，不按「匹配数最多」选 ——
后者在两份都补全了实例名的表上会误降 loose，把不同实例但同位置的连线混为一谈。

### 修掉的三条真 bug（都是「数字看起来正常」的那种）

1. **计数被 `limit` 截断**：`limit=30` 时把 `len(diff.added)` 当条数 → 4886 条新增报成「30 行」。
   用户看到 30 会以为改动很小。原单测断言写的是 `total_changes >= 5`，`5 >= 5` 通过 —— 漏网了，改成精确值断言。
2. **计数被同名字段覆盖**：`device_payload` 把 counts 展开进 payload 顶层，又用同名键写样本列表，
   后者覆盖前者 → 前端 `.toLocaleString()` 得 `"undefined"`。计数与样本必须用不同的键。
3. **两个长度列被认成一个**：25 列表格有 `线缆长度1`（公式算出的计算值，idx 19）与
   `线缆长度`（人工核定值，idx 20）。原映射把两者塞进一个字段，`线缆长度1` 先命中占掉位置，
   真正的核定值被丢弃 → diff 拿「计算值」去比「核定值」，两份都对的数据会报成一片差异。

### 应用层依赖倒置（`lint-imports` 抓到的真违规）

`compare.py` 最初直接 `from ...infrastructure.xlsx.stock_reader import read_stock_table`，
契约第 4 条「应用层不得依赖基础设施」立刻 BROKEN。
改成函数体内 `import` 想绕过 —— **仍然 BROKEN**，import-linter 会扫描函数体内的 import 语句，
它拦的正是「延迟导入」这种假解耦。

真解法是把装配点挪到组合根：`create_app()` 里 `set_stock_reader(XlsxStockReader())`，
应用层只在调用时从注册表取，代码里不出现任何 `infrastructure` 名字。

## 十、v0.5 已完成（跑得起来：设备台账 / 端口台账）

### 这一版回答的问题

v0.4 之前只能回答「哪根线接哪里」。这一版回答三件事：
**这个口用了没**、**这台设备还剩几个口**、**这个型号还能再挂几台服务器**。
扩容决策和施工前复核都靠这个，在 Excel 里要筛选 + 手数。

### 三层结构

| 层 | 文件 | 做什么 |
|---|---|---|
| 端口模板 | `domain/ports/portspec.py` | 26 个型号的标称端口，抄自 `首期设备清单` 的「配置」列原文（如 `36端口100GE板*3 + 48端口25GE板*1` → 108×100GE + 48×25GE） |
| 台账聚合 | `domain/ports/ledger.py` | 连线 → 设备 → 端口条目。端口身份是 `(组, 面板, 序号)` 而不是端口名 —— 同一物理口可能写 `25GE1/0/5` 也可能写 `10GE1/0/5` |
| 服务与入口 | `application/services/portledger.py` + `GET /api/ledger` + `idcbox ledger` + 第十页签「设备台账」 | 三种粒度：按设备 / 按型号 / 按机柜 |

### 端口模板不是手抄一万个口，是 26 个型号的规格

`首期设备清单` 的「配置」列本来就有端口规格文本，所以不需要人工录入 10203 个端口，
只需要 26 个型号的模板 + 人工确认。实测结果：

```
设备总数 954 / 有模板 953 台 / 未知端口 0 / 越界 0
利用率 min=1.9% 中位=77.8% max=100.0%
```

**模板里有两处必须按实测改，不能照抄配置文本**：

- `带内/带外交换机1` 配置写「4 个万兆 SFP+ + 2 个专用堆叠口」，但实测 `10GE1/0/5`、`10GE1/0/6`
  确实在用（存储带内交换机用它做堆叠）→ 那是**同一批 6 个 SFP+ 口位**（编号 1~6），
  不同角色占不同子集。拆成「4 口组 + 2 口组」会让 5、6 号口越界变成未知端口。
- `计算节点A（ARM）` 配置写「四口 25G 网卡」，但布线表一律写 `万兆1..4` → 组名必须用 `万兆`、
  速率集合收 `(25000, 10000)`，否则 2184 行全部报未知端口。

### 三个数字口径（都会影响现场判断）

1. **分母只算有模板的设备**。型号没模板时标称端口数未知，算成 0 或猜一个会让利用率
   凭空变好看 —— 比不给数字更糟。那几台单独列出来，不参与分母。
2. **已用端口 ≠ 连线数**。一条线两端各记一个端口，所以已用 ≈ 连线 × 2。
   实测 10252 ≈ 5127 × 2，差 2 是 `分线接入交换机` 的 MPO 一分三（物理上一个口接三根线）。
3. **无模板显示「—」不显示 0%**。0% 会被当成「全是空的、随便插」。

### 顺带修的两件事（都是「整体统计看不出异常」的那种）

**1. 型号别名**：`广域网负载均衡` 与 `广域网链路负载均衡` 是同一台 2U 设备的两种写法
（实测 ch1 rack5 / rack23 的 U19-20U 同时出现这两个名字）。漏这个别名，
台账上直接少 2 台设备的容量，而整体统计只差 34 口 —— 看不出来。
不做模糊匹配的理由：`业务接入交换机1` 与 `业务接入交换机2` 只差一个字，
但 100GE 口一个是上行一个是堆叠，混成一个比不匹配更糟。

**2. 未知端口的根因披露**：`管理接入交换机-1` 报「模板里没有 `25GE1/0/45`、`46`」，
根因是**源表型号记错**（自报 `业务接入交换机1`、被引用时写 `带外交换机1`），不是模板错。
新增 `modelConflicts` 字段把这个因果关系固定进接口，避免有人去改模板把它改坏。

### 六个必须做对的地方（每条都有实测依据）

| # | 约束 | 实测依据 | 做错的后果 |
|---|---|---|---|
| ★1 | 命名变体必须**合并** | 6 组「同一台设备两个名字」：`备份-1`/`备份一体机-1`、`tgw-1`/`tpgw-1` 等 | 设备数从 824 变 830，端口分散到两台，凭空冒出「未知端口」 |
| ★2 | 真叠放**绝不能**合并 | `ch2/ch8/ch9` 的 `rack11` 31U 上各有一对 `N02-11-S7`/`N02-11-S7-1`，端口集**完全相同** | 台账里少 3 台设备，而这 3 台是规划上真放两台 |
| ★3 | 接线区间按**型号拆行** | 一台交换机同时接两种型号节点（`计算接入交换机(业务)-5` 的 44 口里既有 A 又有 B） | 违反 `UNIQUE(project, switch, model, base_port)`，或把 44 口错算成 1 块 |
| ★4 | `cable` a 侧唯一、z 侧可多根 | `分线接入交换机-2` 的 `25GE1/0/48` 接 3 根 —— 正是 **MPO 一分三** | 加 a 侧唯一约束会导入失败；加 z 侧唯一约束会丢掉一分三 |
| ★5 | 服务器 `name` 必须**可空** | 824 个位置里 **666 个没有名字**，其中服务器 550 / 存储 116 | 用槽位号填充 → 所有按名字分组的功能（「这台改过什么」）把每台当成独立新设备 |
| ★6 | 端口角色取**模板名义角色** | `100GE1/0/1..4` → 核心交换机各 30 次是 uplink；`10GE1/0/48` → 接入交换机是 stack | 按实际连线猜角色，交叉连接的口会被归错类 |

★1 与 ★2 的判据是同一条：**端口集是否相交**。有交集 → 真叠放（保留两台 + 记冲突）；无交集 → 命名变体（合并成一台）。这条判据能同时成立，是因为真实数据里「同一台设备的两个名字」各自只被记了不同的端口，「两台设备的同一位置」端口集必然重叠。

### 落库层的四个约定

1. **确定性 ID，不用 `uuid4()`**：同一自然键永远得到同一个主键。用随机数的话，重跑一次导入就是「换了一套设备」—— 外键全部重接、审计日志里的 `device_id` 全部失效。
2. **按项目划范围**：`device_id(project, key)` 而不是 `device_id(key)`。不这么做的后果是第二个项目的「403 房间」撞主键（`UNIQUE constraint failed: room.id`），或者更糟 —— 两个项目共用同一个型号行，改一个另一个跟着变。
3. **全量重建 + 倒序删除**：`cable.a_port_id` 与 `device_instance.rack_id` 没有级联，删除顺序错了直接 `FOREIGN KEY constraint failed`。
4. **分类要映射**：`core` 落成 `switch` + `role_hint='core'`。`schema.sql` 的 CHECK 只允许 `switch/server/security/balancer/storage/other` —— 分类是采购维度，「核心」是角色维度，混在一列以后统计就得靠字符串匹配。

### 修掉的四个真 bug

| bug | 症状 | 根因 |
|---|---|---|
| 端口从 12770 掉到 7710 | 服务器端口全漏 | `canon_ports` 按 `name` 配设备，而 564 台服务器没有名字 |
| 44 对 `UNIQUE constraint failed: port` | 报错只说是 port 表 | 合并设备的两个台账键各算一遍，同一物理口出两行（一行 occupied 一行 free） |
| `UNIQUE constraint failed: room.id` | 报错参数看得见 ID 冲突 | 确定性 ID 没按项目分范围 |
| 设备只有 456 台 | 368 台设备找不到机柜被静默跳过 | `CanonDevice.side` 恒为 `"N"`（canon 层没有几何快照）；补 `(通道, 柜号)` 备用索引 —— 实测同一通道内柜号唯一确定侧别 |

## 十二、v0.7 已完成（别人也能用：设备型号库）

### 这一版回答的问题

**「我不懂代码，能自己加一个型号吗？」**

v0.5/v0.6 的端口模板是 `domain/ports/portspec.py` 里硬编码的 26 个型号。那 26 条本身是对的（逐条核过 `首期设备清单` 的配置原文），但它意味着：现场来一台自研交换机，就得有人改代码、跑测试、发版。而客户的机房不会只有 26 种设备。

### 三个来源按优先级叠加

| 优先级 | 来源 | 谁维护 | 典型场景 |
|---|---|---|---|
| 1（最低） | `portspec.SPECS` 内置 26 条 | 本仓库 | 底座，永远在 |
| 2 | 项目内 `models.json` | 项目使用者 | 该项目特有的自研设备 |
| 3（最高） | Excel「型号库」sheet | 现场工程师 | 用 Excel 维护，不用碰代码 |

**叠加而不是替换**，这是关键设计：若替换内置表，另外二十几个型号会全部变成「无模板」——表现是台账上大批设备显示「端口未知」，而使用者根本不知道自己做错了什么。要删一个内置型号，得显式写 `{"name": "X", "remove": true}` 或在 Excel 里给该型号打「停用」标记。删除是**显式动作**，不是副作用。

### 怎么用

```bash
# 看当前生效的库（型号、口数、每个型号的出处）
idcbox models

# 导出来交给现场改（两种格式都给，JSON 给开发、Excel 给工程师）
idcbox models --export-xlsx 型号库.xlsx --export-json models.json

# 现场改完叠回去
idcbox ledger   --intent ../projects/v13/intent_full.json --models-xlsx 型号库.xlsx
idcbox decompose --intent ../projects/v13/intent_full.json --models-json models.json --db data/idcbox.db
```

Excel 版式是两段表上下排（型号表 + 端口行表），同一个 sheet —— 现场工程师是「照着设备面板抄一遍」，两段放一起他一眼能看到「这个型号一共几行口」，也方便整块复制粘贴。

### 往返无损的两个前提

**1. 面板号必须显式写死。** `业务核心交换机` 有 3 块同规格 100GE 板，靠 `slots()` 里「同组名出现的先后」编号。导出时不把算出来的面板号写进去，再导入会把三块合并成一块 —— **156 口变 108 口**，数字看着像个正常数字，没人会发现少了 48 个口。

**2. 比对口径不能取 `bays`。** 内置表写 `panel=0`（表示「按出现顺序自动编号」），库里写算出来的 `panel=1`，两者端口身份等价。直接比 `bays` 会让导出一趟再导回来报「改动 26」，用户只会以为导出坏了。所以比较口径定在「展开后的端口身份 + 角色」，也就是台账实际用到的那一层。

## 十三、v0.8 已完成（拖得动：布局段设备也能调 U 位）

### 这一版解决了什么

v0.4 上线拖拽编辑时有个诚实的缺口：**663 台设备（79.5%）拖不动**。
它们由布局段（`RackBlock`）按槽位序列自动排布，意图里没有它们的 `u` 字段，
当时的提示是「拆出来声明成独立设备（这个操作还没做）」。可拖的只有 164 台。

现在 **827 台全部可拖**，剩 7 台仍不可拖（源数据自身位置矛盾，
改哪一行都定不下来，需要先去接线设计里补声明）。

| 类别 | 台数 | 拖动时发生什么 |
|---|---|---|
| 交换机（`switches` 段） | 130 | 直接改那行的 `u` |
| 特殊设备（`devices` 段） | 34 | 直接改那行的 `u` |
| **布局段排布（`layout`）** | **663** | **往 `devices` 段写一条覆盖记录** |
| 源数据位置矛盾 | 7 | 拒绝，提示去补声明 |

### 为什么是「覆盖记录」而不是拆散布局段

布局段是「连续几个机柜全放同型号」的压缩写法 —— V13 里 663 台共用 28 条声明。
为了挪一台去拆散整段，用户要重填几十行。

改为在 `devices` 段加一条：

```json
{"instance": "N02-01-S0", "model": "计算节点A（ARM）", "channel": 2, "rack": 1, "u": 35}
```

`instance` 是**槽位 id** —— `expand_placements` 认它，含义是「这台的位置不用布局段算」。

**槽位 id 不变、只改 U 位**，这是刻意的：换了 node_id 它就不再是交换机组里
第 N 台，端口分配会整体错位（相位轮转规则按节点顺序算）；只挪位置正好表达
「这台换了个机架上位置，线要跟着重接」—— 这是真实世界的语义。

### 五个真 bug

| bug | 症状 | 根因 |
|---|---|---|
| **拖过一次后那台就再也拖不动，而且不报错** | 用户拖了一台，松手成功；再拖一次没反应 | `editable_items` 把覆盖记录按槽位 id 返回，而前端按 `displayName`（型号）比对，永远匹配不上 |
| 布局段设备不算「占用」 | 把交换机拖进计算节点的 U 位不被拦，生成后真叠在一起 | `occupied_spans` 只看 `switches`/`devices` 两段 |
| 不传 `currentU` 时会瞎猜 | 提示「已移到 37U」正确，动的是另一台设备 | 同柜 8 台同型号的 `displayName` 完全相同 |
| 拖动高亮按名字 → 同柜 8 台一起亮 | 拖一台全柜同型号的都变蓝 | `dragging` 键用了 `displayName` |
| 半成品 doc 让整个拖拽面板挂掉 | 编辑器改到一半时拖动报 `AttributeError` | `_layout_spans` 没吞 `AttributeError`（`racks` 里某块写成字符串） |

## 十四、v0.9 已完成（印得出来：线缆标签清单）

### 这一版回答的问题

「明天上架，贴纸怎么打？」前八版都在电脑里：布线表、图纸、台账、耗材清单。
而现场真正拿在手上的是一张张贴纸 —— 一端一张，共 **10254 张**。

### 格式不是设计出来的，是从真表反解的

源文件 `11+12冷通道（示例）.xlsx` 里有现成的标签样例：

```
11A14-39U  存储节点存储网(SRV)  25G1
```

拆成三段就是规则：`{通道号}A{机柜二位}-{U数}U` + 空格 + `{设备编码}({类别})` + 空格 + `{端口名}`。

把规则套回真实 2844 条标签按字符逐个拼 —— **2844/2844 = 100.00% 完全一致**，零差异。
这不是「看起来像」，是逐字符相等。

### 三段里的两个坑

**坑一：机柜的走廊侧别丢掉了。** 平面图上柜号在通道两侧镜像（通道 1 的 1 号柜北侧、27 号柜南侧），
但标签只写 `1A01` —— 不写 A/B 面。于是同一台设备从"北侧 3U"搬到"南侧 3U"标签完全不变。
这是**好事**（现场先看 U 位再看端口），但它意味着标签不能当作位置唯一依据 ——
所以台账页保留 `(通道, 机柜, U位)` 三元组，标签只是它的一个视图。

**坑二：4230 张没有设备编码。** 服务器与存储节点在源 Excel 里**本来就没有实例名**
（`本端设备名称` 列 100% 填的是交换机，服务器行全是空的）。于是这些标签只有「位置 + 端口」：

```
2A01-31U  万兆1        ← 没有设备编码，同柜 8 台同型号服务器无法区分
```

**默认留空并告警，不替你发明名字。** 勾「自动编号」才按 `SRV01..SRV564` / `STG01..STG124`
全项目连续编号，页面上明确写着「这是我们编的，若贵方已有编码规则请先改 `models.json`
或直接在意图里填 `instance`」—— 编出来的设备名进了合同和验收单，改起来比空着麻烦得多。

### 排序按施工动作排，不按表行序

三个层次：**机柜（自然序）→ U 位（从 42 往下）→ 端口（速率降序，再板卡/槽位/序号）**。

- **U 位降序**：打线的人站在柜前是从上往下看的。升序会让他在柜子里来回起伏，300 张标签要弯腰几十次。
- **自然序**：字符串序下 `12A02 < 1A01`（`2`(0x32) < `A`(0x41)），通道 12 会排到通道 1 前面；
  端口更糟，`100GE1/0/10 < 100GE1/0/2`，现场会从 1 跳到 10 再跳回 2。**实测 30 张连续标签里 19 张是乱序的**。
  改成数字分段比较后 `1 < 2 < … < 9 < 10 < 11`。
- **速率优先**：核心交换机 `100GE1/0/1` 与 `25GE1/0/1` 的 (chassis, slot, port) 完全相同，
  只按它们排会交替出 `100G, 25G, 100G, 25G` —— 理线时两种线缆缠在一起。
  按速率分组后是干净的 `100GE1/0/1..52` + `25GE1/0/1..33` 两段。

## 十五、v0.10 已完成（挪得动：跨机柜拖动）

### 这一版回答的问题

v0.8 让 827 台设备能在**柜内**上下挪。但真实现场最常见的一句话是
「这台别装 5 号柜了，挪到 7 号柜」—— 上一版拖到平面图上，什么都不会发生。

### 为什么不能「加个参数就完」

三类设备有**三条完全不同的写入路径**，写错任何一条的表现都是
「松手看着成功了，重新生成跳回原柜」—— 不报错、不崩、数据还在，只是没动：

| 设备来源 | 台数 | 跨柜时改什么 | 目标柜的约束 |
|---|---|---|---|
| 布局段排布（`racks` 段一段 N 台） | 663 | 往 `devices` 段写覆盖记录 | **必须是本通道某个布局段覆盖的柜** |
| 逐台声明（`switches` / `devices`） | 164 | 那一行的 `rack` 字段 | 本通道内**真实存在**的柜即可 |
| 源数据自身位置矛盾 | 7 | 无处可改 | 先补声明 |

第一条的约束来源：覆盖记录靠**槽位 id**（`N02-01-S0`）被 `expand_placements`
认出来，而它只在布局段覆盖的柜上生效。写进一个没有排布的柜，这台设备就
**在库里但排不出来**，布线表里它的线全消失。

第三条是这一版**修掉的一个真 bug**：原先两类设备共用同一条「目标柜必须在
布局段里」的检查。但 ch1 是网络/安全机柜区，**一段布局都没有**（全是逐台
声明的核心交换机）—— 结果是核心交换机一台都换不了柜，提示还很像"这个柜
不存在"，而机柜 5 明明装着分线接入交换机和国密 SSL-VPN。现在拆成两条规则，
逐台声明的设备只要目标柜真实存在（布局段覆盖的 ∪ 已被声明过的）就放行。

### node_id 不能重编 —— 这是这一版最关键的一个决定

跨柜后这台设备仍是「交换机组里第 N 台」，所以 `node_id` 保持不变，只改位置：

```python
# 换柜时若重新分配 node_id（比如按新位置重编成 N02-05-S0），
# 端口分配链里「第几个节点接第几个口」的对应关系整体错位，
# 布线表里这个机柜的 44 根线会全部接到错误的端口上。
```

实测：`N02-01-S0` 从 ch2 rack1 的 3U 拖到 rack5 的 37U 后，
`expand_placements` 里它仍是同一台、位置变成 `(5, 37)`。

### 跨柜时保持当前 U 位，不是"落到鼠标那一格"

落点是平面图上一个格子，那里没有「第几 U」。硬猜一个 U 位等于替用户做
他没表达的决定 —— 而且大概率撞到别人头上。所以跨柜只换柜、U 位不动；
那个位置若已被占，后端拒绝并说清是谁占着：

```
U27-28 已被占用：计算节点A（ARM）（27-28U）
```

用户看清了再点进目标机柜微调 —— 那一步就是 v0.8 已经做好的同柜拖动。

### 前端两个不显眼但必须处理的地方

**一、落点判定不能用 pointerup 的目标元素。** 起点调了 `setPointerCapture`，
捕获期间**所有** pointer 事件都被起点那个 `<g>` 吃掉，平面图根本收不到
`pointerup`。改用 `document.elementFromPoint(clientX, clientY)` 做一次独立
命中测试，再 `closest('[data-rack]')` 读 `data-channel` / `data-rack`。
代价是这条链依赖平面图每个机柜 `<rect>` 上的两个 data 属性 ——
两处必须一起改，否则跨柜拖拽**静默失效**（注释里写死了这句）。

**二、拖走后要滤掉、拖进来要补画。** U 位图画的是**存量布线表**推出的位置，
而拖动改的是**意图**。跨柜后：

- 原柜里那台还在 payload 里 → 不滤掉就是「同一台出现两次」，而且两个方块
  看起来都完全正常，只有把两个机柜并排看才发现。
- 目标柜的 payload 里根本没有这台 → 不补画就是「东西消失了」。

于是 `movedAway` / `movedIntoAt` 两个纯函数各管一头，`MovedEntry` 的 `rack`
拆成 `fromRack` + `toRack`。跨柜成功后自动跳到目标机柜，形成
「拖走 → 落在那边」的闭环。

### 落点高亮三分支

拖动时平面图上：

- **同通道其他柜** = 虚线强调色（合法落点）
- **起点那个柜** = 中性虚线（你现在在这儿）
- **别的通道** = 降透明度**但不隐藏**（隐藏会让平面图突然少一半格子，
  用户以为丢东西了）

规则抽成 `rackDropClass()` 单独测 —— 它错了不报错，只会让人做出错误判断
（同通道没高亮 → 以为不能跨柜拖；别的通道也高亮 → 拖过去才被拒，白拖一次）。

### 跨通道为什么拒绝

换通道等于换一组 ToR 来服务它，那是**重新规划**不是拖动。硬允许的话，
这台设备在端口分配里会「在这个通道里但没人服务」，布线表里它的线全消失。
所以拒绝，并且说清是重规划：

```
不能拖到通道8 —— 换通道等于换一组 ToR 来服务它，那是重新规划。请在「接线设计」里改布局段。
```

## 十六、v0.11 已完成（整摞挪：批量拖动）

### 16.1 这一版回答的问题

上一版能一台一台挪了，但现场动作是「这一摞往下挪 8 格」—— 8 台机器一台台拖，
每拖一台都要重新算「下一台的目标位置是刚才那台的旧位置」。v0.11 让这件事
一次完成。

### 16.2 多选为什么用 Shift 点击而不是框选

框选和拖拽在前 100ms **完全无法区分**：都是「按住左键拉一个矩形」。只能靠
「拉起来的距离」猜，猜错的代价是用户想选 3 台，结果把其中 1 台挪了位置。
Shift 点击没有这个歧义，代价是多点几下（8 台就是 8 下）。

选中状态条给出「已选 N 台」和「清空选择」—— 选错 20 台却只能一台台 Shift
点回去，没人受得了。

### 16.3 批量语义是「同一个 delta」，不是「各自的新位置」

```python
res = move_devices(doc, targets=[...], delta_u=8, target_rack_no=5)
# → moved = ((实例名, 原机柜, 原U, 新机柜, 新U), ...)
```

给每台单独指定新 U 位的话，用户要手算保持相对间距，算错就是设备叠一起。
`delta_u` 天然保住间距，也让「整批能否放下」变成一个可判定的问题。

### 16.4 ★ 这条限制不是性能考虑，是正确性

ch2 机柜 1 有 8 台计算节点占 U 3/7/11/15/19/23/27/31。把 27、31 两台
整体下移 4U（27→31、31→35）时：

```text
单台先挪 27→31  → 失败：U31-32 已被占用：计算节点A（ARM）（31-32U）
move_devices(delta_u=4) → 成功：moved=((『计算节点A（ARM）』,1,27,1,31),
                                          (『计算节点A（ARM）』,1,31,1,35))
```

每台的新位置恰好是下一台的旧位置 —— **逐台校验必然一台都动不了**。
批量端点先把这一批从占用清单里**整体摘掉**，再统一校验。

为什么不能复用单台那个 `occupied_spans(..., skip=...)`：那个 `skip` 只能排
**一台**（`(段名, 行号)` 单值）。批量搬 8 台时剩下 7 台仍站在旧位置，整体下移
会看到「新位置被同伴占着」。`_spans_excluding` 按**身份**（段名+行号 / 槽位 id）
逐台排除，比按 U 区间排除更准 —— 真实数据本来就有 11 对重叠，按 U 排会把
不相干的设备一起摘掉。

### 16.5 修掉一个会挪错设备的真 bug

`_slot_id_at` 在实例名匹配不上时会**退回「按型号 + U 位找第一台」**。
批量拖动于是把「不存在的设备」当成 U3 那台真设备 —— 用户没选它，它被挪了，
而且界面上看不出来。修法：布局段设备的 `instance` 只可能是两种东西
（型号或槽位 id `N02-01-S0`），都不是就直接判「找不到」。

这类 bug 的危险在于**没有任何报错**：批量拖动返回成功，只是动的是别的机器。
发现它是因为单测里写了「未知设备必须被拒绝」，而实际拿到的是
「这一批放不下 … 计算节点A（ARM）（7-8U）」。

### 16.6 五个校验步骤（全部在写之前）

| 步骤 | 判据 | 失败文案要点 |
|---|---|---|
| 1 | 批量非空、`delta_u != 0` | 「没有选中任何设备」/「移动量为 0」 |
| 2 | 所有成员都能定位 | 「意图里找不到『X』」 |
| 3 | 越界 | 指出**是哪一台**：`『X』现在 27U 高 2U，平移 +40 后到 67U 会顶到 68U` |
| 4 | 重叠（含批内互相撞） | 前 3 处逐条列出，多则「另有 N 处」 |
| 5 | 跨柜（整批同一目标柜） | 复用单台规则；一批来自多柜又没给目标柜 → 「要一起移动就得给一个共同的目标机柜」 |

失败时 `doc` **原样返回**（`BatchMoveResult.doc == 传入的 doc`）。批量最容易
出的错是「前 3 台成功、第 4 台失败」，用户看到一半设备动了比整体失败更难收拾。

## 十七、v0.12 已完成（改之前先说清楚：拖动影响面）

### 17.1 这一版要纠正的一句话

v0.8 ~ v0.11 的文档里反复写着：

> 「改 U 位不影响线长：同机柜两端 `path_units = 0`，跳线长度档位不变，
> 所以拖一格不会把 5000 行的线长全改了。它只影响占位冲突与越界。」

这句话**只看到了线长，漏了端口号**。而端口号的影响比线长大一个数量级。

端口分配规则 C2 是 `端口号 = 组内位次 + base`，组内位次按
`(机柜升序, U 位升序)` 排。设备一换柜（或换到不同槽位），它在组里的位次
就变了 —— **同一组里排在它后面的设备端口号整体前移**。

实测（V13 真数据，通道 2 机柜 1 的 `N02-01-S0`）：

| 动作 | 端口重编号 | 位置变化 | 线长变化 |
|---|---|---|---|
| 柜内 3U → 5U（同槽位） | 0 | 7 | 0 |
| 柜内 3U → 35U（同一轮内第 8 槽） | 0 | 7 | 0 |
| **柜内 3U → 39U（落到第 10 槽）** | **56 行 / 7 台** | 7 | 6 |
| **跨柜 机柜1 → 机柜5** | **91 行 / 7 台** | 7 | 6 |

所以连「同柜内挪就安全」也是错觉 —— 换个 U 就可能换位次。

这不是 bug，规则就是这样的，真实 Excel 也这样。但它是**用户看不见的**：
旧界面拖完只显示「已移到通道2 机柜5 的 3U」。

### 17.2 危害为什么特别大

两种人不是同一个人：

- 决定「这台别装 5 号柜了」的是操作电脑的人；
- 拿着布线表去插线的是现场另一个人。

前者看到「已移到 5 号柜」，以为只动了一台；后者按表插线，
91 行端口号已经变了，**全部插错口**。而这件事在界面上没有任何痕迹。

### 17.3 做法：每次拖动都报影响面

新增两个能力：

| 能力 | 位置 |
|---|---|
| `POST /api/intent/impact` **干跑**（不改 doc） | `api/main.py` |
| `POST /api/intent/move`、`/move-batch` 响应带 `impact` | 同上 |
| `domain/ports/gen_diff.py` 生成结果差异（纯函数） | 域层 |
| `application/services/impact.py` 影响面编排 | 应用层 |
| `web/src/domain/impact.ts` 文案（纯函数、可单测） | 前端 |
| RackView 横幅 + 撤销按钮 | 前端 |

**身份键不含端口号**，这是关键：要检出的正是「端口号变了」。
若端口号进身份键，`10GE1/0/1` 消失 + `10GE1/0/33` 新增会被报成
「删 1 行、加 1 行」—— 那是**改设计**，而实际是**同一根线换了口**（重打标签）。
两件事的处置完全不同。

三条口径必须分开说：

| 类别 | 含义 | 处置 |
|---|---|---|
| `portChanges` | 同一根线换了口 | 重打标签 |
| `lengthChanges` | 线长档位变了 | 改采购/施工 |
| `added` / `removed` | 接线拓扑变了 | 重新看设计 |

### 17.4 `lengthChecked` 这一位是防说假话的

源文件缺失时几何取不到，线长就**没算**。这时 `counts.lengthChanges` 是 0 ——
但「没算」和「没变」是两件事。若界面说成「线长没变」，用户会以为安全。

所以 payload 单列 `lengthChecked`，界面据此说「**线长未校验（缺平面图源文件）**」。
这也是为什么 `move` 端点不因为几何缺失就 500：拖动是纯意图操作，
不该绑死在「必须先有 Excel」上。

### 17.5 顺带修掉一个同类的真 bug：单台路径会挪错设备

v0.11 给批量路径加了一道名字白名单（见 §16.5）：布局段设备的 `instance`
只可能是型号或槽位 id，都不是就判「找不到」。**单台路径漏了这道守卫。**

于是 `POST /api/intent/move` 传一个不存在的名字时：`_guess_model` 只看机柜
属于哪个布局块（不看名字）→ 拿到 `计算节点A（ARM）` → `_slot_id_at` 退回
「按型号 + U 位找第一台」→ 命中 `N02-01-S0` → **成功改掉那台真机的位置**，
返回 `ok=true`。而同样的动作走 `/api/intent/move-batch` 会被正确拒绝。

两个入口对同一件事给出相反答案，比两个都错更难发现 —— 因为用户会以为是
「单台能拖、批量不能拖」。现在两个入口共用同一道判据。

### 17.5b 松手之前就要知道（干跑预演）

影响面横幅是松手后才出现的 —— 那时已经改了。用户看到「91 行端口号变了」
想反悔只能撤销，而撤销本身也是一次移动（又是 91 行）。

所以拖动过程中每 220ms 问一次 `POST /api/intent/impact`（`deep=false`）：
**26 次 pointermove 只发 6 个请求**，横幅上写着「松手会：21 行端口号会变」。
用户可以在手指还没松开时把设备拖到别处。

**措辞必须与结果不同**：

| 状态 | 文案 | 含义 |
|---|---|---|
| 拖动中 | 「**松手会**改 21 行端口号」 | 还没发生，还能反悔 |
| 已落手 | 「**这次改动影响**：21 行端口号变了」 | 既成事实，只能撤销 |

混用会让用户分不清自己在读预测还是读结果，从而错过唯一还能反悔的窗口。

预演用虚线边框 + 低饱和蓝，已落手用实线 + 黄/红 —— 扫一眼就能分出。

### 17.5c 一个查了三轮的「拖动忽然完全不生效」

加预演之后，拖完松手**什么都没发生**：不发请求、不报错、notice 空着。

查证顺序（前两轮都是误判）：

1. 以为是 CDP 脚本问题 → 换成之前能跑通的脚本，**也失败**，说明是代码；
2. 以为是 `uAtPointer` 越界 → 加探针，`target` 确实为 `null`，
   但那是**我的脚本落点计算公式错了**（用 `.rack-body-wrap svg` 的 rect
   去反算 U 号，而 `uAtPointer` 用的是 `svgRef` 那个 svg，两者尺寸不同）；
3. 改对落点后**仍然失败** → 加探针读到 `finishDrag` 里 `target=null` 消失、
   请求仍不发……最后定位到 **React 闭包快照**。

根因：`finishDrag` 是 `useCallback([draft, ...])`，预演每次 `setPreview(...)`
都让 `draft` 变成新对象 → `finishDrag` 重建 → 重新绑定 `onPointerUp`。
但浏览器里**已经发生**的那次 pointerdown 之后，松手时的 `pointerup`
用的仍是**按下时那一次渲染**的 handler，它闭包里的 `draft` 是旧的。

修法：`onPointerUp` 走 `finishDragRef.current`，`ref` 永远指向最新那份。
同时 `dragging` 的判定也改成读 `draggingRef`（同一个原因）。
（教训也写进了 `AGENTS.md` §6.6。）

### 17.6 撤销：为什么是必需品而不是锦上添花

看到「91 行端口号变了」的人第一反应是撤销。若没有撤销，他只能自己拖回去 ——
而**拖回去又是一次移动，又是一次 91 行端口变化**，而且这次连「原本什么样」
都得靠记忆。所以草稿里留一份上一版文档快照。

只留**一步**：更多步要的是版本库（「保存为版本」已经能做），在草稿里做
多步撤销栈会让「现在到底改了什么」更难说清。

### 17.7 设备名不能是内部 id

横幅第一版显示：

```
计算接入交换机(业务)-1 → N02-01-S6（万兆1）：10GE1/0/7 → 10GE1/0/6
```

`N02-01-S6` 是程序内部槽位 id，**机器上没有任何东西写着它**，现场拿着它
找不到任何一台机器。现在翻成 `计算节点A（ARM） 机柜1 27-28U`。

同一个判据在 `labelsvc.py` 里也有一份（防止槽位号漏进贴纸）。
两处都要的理由相同：**内部 id 一旦流到人眼前，就一定有人照着它做事**。
有一条测试直接对整个 payload 做正则扫描，出现槽位 id 就红。

### 17.8 性能：为什么要两个 `deep`

| 口径 | 耗时（实测） | 用途 |
|---|---|---|
| `deep=true`（含线长重算） | 约 90ms | 松手前最后一次 |
| `deep=false`（只比端口与位置） | 约 55ms | 拖动过程中 |

一次全量（生成 33ms + 桥 13ms + 算长 74ms）约 120ms，两次正好卡在 NFR-1
的 200ms 增量预算边缘。线长只重算「位置变了的行」（端口重编号不改变机柜坐标，
N/O 只看机柜 → 长度不可能变），省掉 90% 的重算。

### 17.10 为什么真机验证要用 CDP 手写

仓库里没有 playwright / puppeteer，而这个项目要离线交付 ——
为截一张图往依赖里加几十 MB 的浏览器驱动不合适。Node 自带 WebSocket，
直连 Chrome 的 CDP 就够：`Page.navigate` + `Input.dispatchMouseEvent` + `Page.captureScreenshot`。
拖拽要分 24 小步发 `mouseMoved`，原因是真实手拖会连发几十个 pointermove，
只发一次时 `uAtPointer` 可能还没算出落点。

**顺带纠正一次误判**：第一次验证时拖的是最上面那台（31-32U）到 39U，
横幅没出现，我一度以为是 bug。实际是对的 —— 端口位次按 `(机柜, U)` 升序，
最后一台挪到更高的 U 仍在最后，顺序没变、端口号不变。**只有拖排在第一位的
那台越过整轮，后面 7 台的位次才会整体前移。**

### 18.2 渲染账：8 个 draw call，软渲染 60fps

`docs/research/02-visualization-stack.md` §3.2 算过账，实测对上了：

| 物件 | 数量 | 渲染方式 | draw call |
|---|---|---|---|
| 机柜 | 362 | 1 个 InstancedMesh | 1 |
| 柜顶亮条 | 362 | 1 个 InstancedMesh | 1 |
| 设备 | 834 | 按 U 数分 6 组 → 6 个 InstancedMesh | 6 |
| 地板 | 2 | 2 个 Mesh | 2 |
| **实际合计** | | | **10** |

**实测帧率 60.26fps**（181 帧 / 3.0 秒），且是在 **SwiftShader 软件渲染**下 ——
`--disable-gpu --use-gl=swiftshader`，即**完全没有显卡**。AC-7 要求 30fps，
实际是它的两倍。这意味着客户现场的跳板机（通常无独显）也能跑。

> 这条比「在有独显的机器上跑 120fps」有价值得多：**验收环境往往是跳板机**。

`devices.map(d => <mesh/>)` 这种写法在代码里有一条注释明确禁止 ——
3000 个 Mesh = 3000 draw call，会掉到 15fps 以下。这是**代码规范级**的约束。

### 18.3 与 2D 共用一个几何真值（不是"两套坐标"）

| 事实 | 唯一来源 |
|---|---|
| 柜宽 600mm | 布线表 R 列 `0.6m/柜位`（就是线长公式里那个 0.6） |
| 42U = 1866.9mm | EIA-310 标准 1U = 44.45mm × 42 |
| 通道净宽 1200mm | 实测约 1.2m |
| 设备类别 → 颜色 | 后端 `svg.py::categorize()`，3D 只消费不重判 |

**为什么分类必须后端给**：`categorize()` 的判定顺序是硬约束（「核心」必须在
「交换机」之前，否则 `业务核心交换机` 会被画成接入色；「服务器密码机」必须
归安全而不是服务器）。前端复制一份迟早会歪 —— 歪了的后果是**屏幕上红色、
纸上黄色，现场以为拿错了图**。这条在 2D 那边已经踩过。

单位口径：数据里**只有毫米**。`mmToWorld(mm) = mm / 1000` 是**全项目唯一的
/1000**（three 的世界单位是米）。多一处换算就多一处差 1000 倍的机会，
而那种 bug 的表现是"画面全空"，看不出方向。

### 18.4 修掉三个「看着像那么回事」的几何错

这三个都不会报错、不会崩，只是**画出来不对**，只能靠数值断言 + 截图发现：

**① 两排柜穿模（通道消失）**

第一版按「平面图行号 × 600mm」算 z。但平面图一行是**柜位格距**，
而柜深是 **1200mm** —— 北侧柜（行 3）与南侧柜（行 4）只隔 600mm，
两个 1200mm 深的柜子直接互相穿进去。3D 里看是一整块实心长方体，
完全看不出这是两排柜、更看不出中间有通道。

正确算法：`z(通道 c 北侧) = c × (2×柜深 + 通道宽)`、南侧再 +（柜深 + 通道宽）。

**② 两个房间完全重叠（146 个柜坐标重复）**

403 房用列 23..38、404 房用列 3..18，**两间房的列号各不相同**。
两间房都按「减本房最左列」算 x，于是 403 的柜 1 和 404 的柜 1
拿到**完全相同**的世界坐标。3D 里表现为「一个房间，柜数翻倍」，
两个房间的设备混在一起。

修法：按房间号字典序横向排开，房间之间留一条通道宽的空隙。

**③ 相机算错，机柜只在画面中间占一小块**

第一版用 `hypot(宽, 深)` 当画面需要覆盖的尺寸。机房的形状是
**扁而长**（20400 × 2000 × 25200mm），这样算出 49 米距离。

错在：俯视时「深度」大部分被压进屏幕纵轴，不是全部占画面；斜视时
投影范围还随视角变化 —— **不存在一个不依赖视角的固定答案**。

修法：把包围盒 8 个角投影到相机自己的 right/up 轴上，分别按垂直/水平
视场角求距离取较大者。这对任意 theta/phi 都成立，换机房不用调参数。

顺带修掉「注视点在地板」—— 那会让整个场景挤在画面上半部、下方一片空白。

### 18.5 柜体怎么画：试了三种，只有第三种对

这是这一版花时间最多的地方，三个方案都有真实的失败：

| 方案 | 结果 |
|---|---|
| ① 半透明实体（opacity 0.22~0.35） | 362 个透明盒子互相叠加，WebGL 对同尺寸物体排序不稳定 → **一整片黑雾，后排糊住前排** |
| ② 半透明实体 + `EdgesGeometry` 线框 | 线框在 `InstancedMesh` 里是 `LineSegments`，SwiftShader/ANGLE 下渲染成**放射状尖刺** |
| ③ **`BackSide` 不透明盒 + 顶面亮条** | ✅ 采用 |

方案②的失败特别值得记下来：它**在有独显的真机上可能是正常的**，
只在软件渲染下出问题。而客户现场很可能就是没有独显的跳板机 ——
**不能赌它有硬件加速**。这正是「必须在软渲染下验收」的价值。

方案③的原理：`side: BackSide` 只画内壁。正面被剔除，视线直接穿到
柜内设备上；但侧壁与底面的内表面仍参与深度测试，于是每个柜看起来
像一个**敞开的抽屉**。既没有透明排序问题（材质仍是不透明），
又能看见柜里的设备。这是 3D 里做「看得进去的柜子」的经典做法。

顶面亮条用 `FrontSide`（跟柜体相反）—— 否则它跟着翻到柜底，柜顶一片空。

### 18.6 数据与交互

**端点 `GET /api/scene`**（40 个端点里的第 28 个 GET）：

两者取数形状本质不同（2D 要格子、3D 要实心盒 + 朝向；2D 点进柜才要设备、

**102 个请求才能画出第一帧**。

点击判定有个坑：拖动结束那一下也会触发 `click`。用「按下到抬起位移 < 4px」
区分 —— 不加这个判断，**每次转视角都会误跳去某个机柜**。

### 19.2 为什么不能打 venv 的主意（这是绿色包最常见的死法）

把开发机的 `backend/.venv` 压进 zip 是新手包必踩的坑：venv 的
`pyvenv.cfg`/脚本 shebang 全是**绝对路径**，`.so` 又是**平台绑定**的 ——
换机器、换目录、换操作系统三种各有不同死法，而且都死得静默。
绿色包的正确形态是三件事分开：

| 件 | 用什么 | 为什么 |
|---|---|---|
| 解释器 | python-build-standalone `install_only_stripped`（linux 31MB + win 21MB） | 可重定位、双平台各带一份，「**含运行时**」不是嘴上说说 |
| 第三方依赖 | `uv pip install --target` 按 linux / windows 各装一次再**合并** | 平台二进制文件名互不冲突（`*.cpython-312-x86_64-linux-gnu.so` vs `*.cp312-win_amd64.pyd`），纯 Python 两边相同覆盖无害 → **一个包同时能跑两种系统** |
| 我们的代码 | 源码进包 + `PYTHONPATH`，**不走 pip install** | 目标机没有构建隔离（hatchling 拉不到），而 `python -m uvicorn` 根本不需要安装 |

现场启动 = 一行 `run.sh` / 双击 `run.bat`，**全程零 pip、零网络、零写系统目录**。

### 19.3 供应链红线：钉死 + 校验，不是「下载下来能用就行」

这套包是要进客户内网的，所以：

- CPython 3.12.11 / PBS tag `20250918` / 双平台 **sha256 写死在脚本里**；
- **缓存命中也要过哈希校验**（缓存本身可能被污染）；
- 依赖版本与 `pyproject [infra,api]` 逐字一致 —— 也就是 1328 用例 +
  导出铁线 0 格差异实测通过的那组版本。

下载源：GitHub 直连被 CDN 节流（HEAD 200、body 超时），gh-proxy 系全灭、
TUNA 未同步 —— 最终走 npmmirror binary 镜像，`--python-mirror` 可覆盖。
**镜像只是换个腿，哈希才是守门人。**

### 19.4 顺手补掉的一个老洞：`pyproject` 里根本没有 `api` extras

`scripts/run.sh` 的报错提示一直让人装 `-e 'backend[infra,api]'`，但 `api`
组**从来不存在** —— 开发机的 fastapi/uvicorn/sqlalchemy 全是 uv 散装的。
后果：依赖清单不可复现、绿色包不知道该带哪些 wheel、新机器照 README
装完起不来。这一版补上并全部钉版本。**打包逼出来的第一个受益者是自己**：
没有这份清单，`uv pip install --target` 连该装什么都要靠猜。

### 19.5 三个「验证脚本/工具自己坑自己」的时刻

这一版一半时间花在排除**不是产品的 bug**：

1. **自检把 curl 也走了死代理**：模拟断网用 `http_proxy=127.0.0.1:9`，
   结果对 `127.0.0.1:8123` 的本地探测也被代理劫持 → 永远「未就绪」。
   本机探测必须 `--noproxy '*'`。**模拟断网的工具自己也得懂网络。**
2. **`( cd … && ./run.sh ) &` 的 `$!` 是 subshell 的 pid**，`run.sh` 里
   `exec python` 替换的是它的**子进程** → trap 杀错人 → 自检留下一具
   占着端口的僵尸服务，把下一轮自检挡死。子 shell 里显式 `exec` 让
   run.sh 顶替 subshell，pid 才对得上。
3. **`pkill -f "uvicorn idcbox…"` 在 `bash -c` 里会匹配到执行它的 shell
   自己**（pattern 字符串就在本命令行上）—— 一次 `SIGTERM` 自杀收尾。
   清理改用「先 `ss` 查 pid 再 kill」或在**脚本文件**里执行。

`.bat` 必须 CRLF 也算半个：LF 写的 `if (...)` 多行块在 cmd 里直接
「命令语法不正确」，而这个问题**在 Linux 上永远测不出来** ——
产物校验里加了 `file run.bat` 检查。
